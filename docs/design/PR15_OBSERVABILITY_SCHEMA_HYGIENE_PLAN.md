## 2. Timezone Policy

### Python

**Policy: use `datetime.now(timezone.utc)` everywhere a Python-side UTC "now" value is needed.** `datetime.utcnow()` is deprecated in current Python guidance because it returns a **naive** datetime that silently claims no timezone while implicitly meaning UTC — a footgun for any comparison against a timezone-aware value (which is exactly the mix this repository currently has, per §2.2 below). This applies to every `datetime.utcnow()` call site identified in §3.1.

### Database — authoritative source per timestamp

Every timestamp column must be classified as either **database-authoritative** (the value is computed by PostgreSQL at write time, via `server_default=func.now()`/`onupdate=func.now()`) or **application-authoritative** (the value is meaningful application state that Python decides, e.g., "the moment a login succeeded," which the database cannot know on its own). This is not a mechanical choice — it follows the existing, already-established pattern in this codebase:

| Column | Classification | Justification |
|---|---|---|
| `*.created_at` / `*.updated_at` (all tables) | **Database-authoritative** | Row creation/modification instant is exactly what `server_default=func.now()`/`onupdate=func.now()` exists to guarantee — it cannot be spoofed by client clock skew or a slow request, and it's already the established pattern via `TimestampMixin` for `Equipment`, `BorrowTransaction`, `User`. |
| `AuditLog.created_at` | **Database-authoritative** | Same reasoning — an audit row's timestamp must be the moment PostgreSQL actually committed it, not a Python-computed value that could predate a slow transaction's actual commit. |
| `Notification.created_at` | **Database-authoritative** | Same reasoning as above; no reason for this to differ from the `TimestampMixin` pattern. |
| `EquipmentStatusHistory.changed_at` | **Database-authoritative** | The history row's timestamp should reflect when the status-history row was actually written, consistent with every other `*_history`/`*_log` table's pattern. |
| `BorrowTransaction.borrowed_at` | **Database-authoritative** | This is the dispatch-transaction's creation moment in all current call sites (`app/services/borrow_service.py` sets it at transaction-creation time) — functionally a creation timestamp, should follow the same server-computed pattern as `created_at`. |
| `BorrowTransaction.returned_at` | **Application-authoritative, but must use `datetime.now(timezone.utc)`** | Set at receipt time in `app/crud/transaction.py`, inside the same request/transaction that also validates the conditional-`UPDATE` receipt-race outcome (Roadmap PR8A) — the value must be assigned in Python because it's coupled to that transaction's business decision, not purely "when did this row get written." Converting this to `server_default`/`onupdate` would be a larger behavioral change than a hygiene pass should make. |
| `BorrowTransaction.due_at` | **Historical, read-only — no write path exists** | Verified via full-repository grep: `due_at` is only ever *read* today (`app/services/report_service.py`), never written by any current code path — the due-date workflow was removed in Roadmap PR7a and this column is preserved history only. Its type should still be corrected for consistency, but there is no live write-path behavior to change. |
| `User.last_login_at` | **Application-authoritative, must use `datetime.now(timezone.utc)`** | Set in `app/services/auth_service.py` at the moment a login is confirmed — this is already declared `DateTime(timezone=True)` in the model (confirmed by inspection), but the Python-side value assigned to it (`datetime.utcnow()`) is naive. This is the one column where the **column type is already correct** (`timestamptz`) but the **Python value being written into it is not** — the narrowest, most surgical fix in this whole policy: change the call site from `datetime.utcnow()` to `datetime.now(timezone.utc)`, no migration needed. |

### PostgreSQL — actual current column types (inspected, not assumed)

Per the review's explicit instruction, every column type below was inspected directly against a live PostgreSQL 16 instance, rehearsed `base → head` (not a stale local database — see §2.0 methodology note: a locally cached `mep_test_db` was found to be stamped past several migrations without having actually executed their raw-SQL `ALTER TABLE` statements, which would have produced false readings; a fresh scratch database rehearsed through every migration from `base` was used instead for all findings in this document).

**Already `timestamp with time zone` (aware) — no migration needed:**
- `equipment.created_at`, `equipment.updated_at`, `equipment.deleted_at`
- `borrow_transactions.created_at`, `borrow_transactions.updated_at`
- `users.created_at`, `users.updated_at`, `users.last_login_at`

**Currently `timestamp without time zone` (naive) — migration candidates:**
- `audit_logs.created_at`
- `notifications.created_at`
- `equipment_status_history.changed_at`
- `borrow_transactions.borrowed_at`
- `borrow_transactions.due_at` (read-only history, per the table above)
- `borrow_transactions.returned_at`

### Conversion expression and historical-data interpretation

If PR15B proceeds with converting the naive columns above to `timestamptz`, the interpretation of **existing stored values** must be stated explicitly, not left implicit: every naive value in this codebase today was written by `datetime.utcnow()`, which — despite being naive — always represents a UTC instant (that is what the function computes; the bug is the missing timezone label, not wrong wall-clock math). Therefore the correct, meaning-preserving conversion is:

```sql
ALTER TABLE audit_logs
  ALTER COLUMN created_at TYPE timestamptz
  USING created_at AT TIME ZONE 'UTC';
```

`AT TIME ZONE 'UTC'` here means "interpret this naive value as having been UTC all along," which is accurate for every existing row (they were all produced by `datetime.utcnow()`). This is **not** the same as `created_at::timestamptz`, which would instead interpret the naive value using the database session's current timezone setting — silently wrong unless the session timezone happens to already be UTC. The design must state this distinction explicitly to avoid a real historical-data corruption risk if implemented carelessly.

### Rollback limitations

Downgrading `timestamptz` back to `timestamp` (`... USING created_at AT TIME ZONE 'UTC'`, the inverse expression) is lossless for the *value* (the same UTC instant, just re-stripped of its label) but is **not** a no-op with respect to correctness going forward: any code deployed against the timestamptz schema that started relying on timezone-aware comparisons would silently regress to naive-comparison behavior after a downgrade. This must be called out explicitly in the migration's downgrade docstring (matching this repository's established pattern — see e.g. migration `0004`'s downgrade docstring on destructive-vs-non-destructive framing) rather than presented as a risk-free revert.

### Required testing

Per the review's explicit instruction, this is not a mechanical replacement — the design specifies these test dimensions for PR15B before implementation:
1. **Historical upgrade** — rehearse against a database seeded with rows at the `0010`/pre-`0011` baseline (naive timestamps with real historical values, not empty tables) to prove the `AT TIME ZONE 'UTC'` conversion preserves the exact instant for pre-existing data, not just for empty/fresh tables.
2. **Downgrade** — prove the reverse conversion is lossless for the stored instant, and that the downgrade docstring's caveat above is accurate.
3. **Re-upgrade** — the same round-trip discipline every migration since `0004` has followed.
4. **Serialization** — confirm FastAPI/Pydantic response serialization of the now-aware datetimes produces the same wire format shape existing frontend code expects (ISO-8601 with an explicit offset, e.g. `+00:00`, versus the previous naive `...` with no offset) — this is a wire-format change even though it is not an intentional API contract change, and must be verified against `frontend/src/types/index.ts`'s parsing expectations before merge, not assumed compatible.
5. **SQLite/PostgreSQL compatibility** — the SQLite test path (`Base.metadata.create_all()`, used by the non-PostgreSQL test suite) does not enforce `timestamptz` the way PostgreSQL does; confirm the ORM-level `DateTime(timezone=True)` type still round-trips correctly through SQLite's storage (SQLAlchemy's SQLite dialect stores timezone-aware datetimes as ISO strings and can lose the tzinfo on read-back unless handled carefully) so the two dialects' test suites don't silently diverge in what they're actually verifying.

**This policy explicitly rejects treating the timezone migration as a mechanical `datetime.utcnow()` → `datetime.now(timezone.utc)` find-and-replace.** The column-type change, the conversion-expression correctness, and the serialization-shape impact are all first-class design concerns, addressed above before any implementation.

## 2.2 Corrected Existing-State Assessment (replacing Revision 1's errors)

Revision 1 accurately identified some already-resolved findings but this revision restates them precisely, per the review's correction:

- **Application-level access logging is still absent.** `request_context_middleware` only sets response headers; no line is logged per completed request (method/path/status/latency). Confirmed still true.

## 4. `PMSchedule` / `CalibrationSchedule` — Deferred, Not Proposed for Removal

Per the review's explicit instruction, this revision does not propose removing these tables. Acknowledged directly:

- **Possible production data:** although no code path in this repository currently reads or writes these tables, this design has no visibility into whether any out-of-band process (a manual DB script, a future partially-built feature, direct administrative data entry) has ever written rows into them. Absence of application-code references is not proof of an empty table in every real deployment.
- **ORM/`0001` bootstrap implications:** these tables are created by `Base.metadata.create_all()` inside migration `0001_initial.py` (the same TD-002 behavior already governing every other model) — removing the ORM classes would remove them from a fresh install's schema, while an existing deployment would still have the tables until a dedicated `DROP TABLE` migration ran. This asymmetry must be resolved by a real migration, not just deleting the model classes.
- **Fresh/upgraded schema convergence:** any removal must be verified to converge identically on both paths — fresh install (no tables from the start) and historical upgrade (tables dropped by migration) — matching this repository's established migration-testing discipline.

**Disposition: Deferred.** If future removal is desired, it requires, in order: (1) explicit Repository Owner approval that PM/Calibration scheduling is not near-term confirmed work, (2) a dedicated migration (not bundled into PR15B's other changes), (3) a data preflight step confirming zero rows exist in any real target deployment before the `DROP TABLE` runs, and (4) the same fresh/historical/downgrade/re-upgrade convergence testing every schema-bearing PR in this repository already follows. This is sized as its own small follow-up PR, not PR15B scope.

## 5. PR15A Scope — Observability Only

**Explicitly excluded:** schema migrations, timezone migrations, constraint changes. Nothing in PR15A touches the database.

**Included:**
1. **Structured logging.** Replace `logging.basicConfig`'s plain-text formatter with a JSON formatter in `app/core/logging.py`.
2. **Request/correlation IDs, reusing the existing mechanism.** `request_id`/`correlation_id` are already generated and validated by PR3's `request_context_middleware` (`app/main.py`) — PR15A does not create a second ID mechanism, it propagates the existing one into log records.
3. **Async-safe context propagation.** Use a `contextvars.ContextVar` (not a global/thread-local, which is unsafe under `asyncio`'s cooperative concurrency — a thread-local would leak or cross-contaminate between concurrently-scheduled requests sharing the same OS thread) populated by the middleware and read by a `logging.Filter` attached to the root logger, so every log line emitted during a request's async call chain — including from service/CRUD-layer code that has no direct access to the `Request` object — automatically includes `request_id`/`correlation_id` without threading them through every function signature.
4. **One access-log event per request.** Emitted from `request_context_middleware` after `call_next` returns, logging method, **route template** (not raw URL — see next point), status, and latency.
5. **Route templates rather than raw URLs.** Use `request.scope.get("route")`'s templated path (e.g. `/api/v1/equipment/{equipment_id}`) rather than `request.url.path` (e.g. `/api/v1/equipment/3f2a...`) — using the raw URL would make every equipment/transaction/user detail request a distinct high-cardinality log key, defeating aggregation and creating an unbounded label-cardinality problem for any future metrics work.
6. **Background-job run IDs.** `check_pm_cal_due()` generates one correlation ID per scheduled run (mirroring the per-request ID, but scoped to the job invocation, not an HTTP request), included in its start/success/failure log lines, plus a `try/except` wrapping the job body with `logger.exception` on failure and duration logging on both branches.
7. **Aggregate import logging.** One `logger.info` line in `import_service.py` on successful commit, mirroring the existing audit-log summary (`total_rows`/`succeeded`/`failed`/`skipped`).
8. **Logging isolation from transaction outcome.** New log statements must never be placed such that a logging failure could affect a database transaction's commit/rollback decision, and conversely a transaction rollback must never suppress a log line that already correctly described what was attempted — mirrors the existing best-effort-audit isolation principle already established in `app/core/audit.py` (`record_best_effort_audit_event`/`commit_best_effort`). Logging calls are synchronous, in-process, and outside the database session entirely, so this is a design invariant to preserve, not new mechanism to build.

**Planned regression coverage** (using `backend/tests/test_redis_failure_logging.py`'s established `caplog` pattern):
- **Concurrent request isolation:** two simulated concurrent requests with different `request_id`s must never have their IDs cross-contaminate in captured log records — the direct test of the `contextvars` approach's correctness under `asyncio` concurrency.
- **Invalid IDs:** an inbound `X-Request-ID`/`X-Correlation-ID` header that fails `_safe_inbound_id`'s existing validation must not appear in any log line (the freshly-generated fallback ID must be what's logged, not the rejected client-supplied value).
- **Exception paths:** each of the four exception handlers in `main.py` must produce a log record containing the request's `request_id`.
- **Exactly-one access event:** a single request must produce exactly one access-log line, not zero (silently dropped) and not more than one (double-logged via a retry/duplicate registration bug).
- **Sensitive-data non-persistence:** no new log line may include a password, JWT, refresh-token JTI in cleartext, or `RequestValidationError`'s raw `input`/`ctx` — mirrors the existing `_redact()`/validation-handler discipline and must be asserted, not just assumed.

## 6. PR15B Scope — Schema Hygiene Only

**New migration:** `0012_*.py` (the next number after `0011_pagination_ordering_indexes.py`).

ADD CONSTRAINT` itself fail with an opaque PostgreSQL error).

**Included:**

3. **Index naming standardization**, rename-only: bring the 4 GIN trigram indexes and `idx_tx_one_active_borrow` onto the same naming convention as the other 34 indexes (or vice versa — the specific target convention is an open question for approval, see below), via `ALTER INDEX ... RENAME TO ...`, zero behavior change.
4. **`Notification.type` comment fix** and **`docs/TECH_DEBT.md` TD-001 status correction** — documentation-only, bundled into PR15B's cleanup pass since they touch the same files as the rest of this PR's review, not because they need a migration.

**Explicitly excluded from PR15B:** FK index additions (§ below), `PMSchedule`/`CalibrationSchedule` removal (§6 above — deferred), `users` soft-delete (§1 — deferred), any further `CHECK` constraint beyond what's already justified in §1.

**FK index work remains evidence-gated and stays outside PR15B**, per the review's explicit instruction and the precedent PR14B's own review established: any future FK-index addition needs `EXPLAIN ANALYZE` proof against a representative query shape, not a blanket "unindexed FKs should be indexed" pass. Not proposed as part of this PR at all.

**PostgreSQL migration testing:** fresh install (`base → head`), historical upgrade (`0011 → 0012`), downgrade, re-upgrade — the same four-path discipline every migration since `0004` has followed, run against real PostgreSQL 16, not SQLite.

**Rollback limitations:** stated explicitly in the migration's downgrade docstring for the timestamptz conversion (§2, "Rollback limitations" — value-lossless but a real regression risk for any code that started depending on aware-datetime comparison semantics); the `ondelete` policy changes and index renames are fully reversible with no data-loss caveat.

**Fresh/historical schema convergence:** verified identically to every prior schema-bearing PR — a fresh `base → head` install and a historical `0011 → 0012` upgrade must produce byte-identical resulting schemas (column types, constraint definitions, index names), captured as an automated regression test following the pattern already established in `backend/tests/test_postgres_integration.py`.

## 7. Open Questions for Architecture Approval

1. **`ondelete` policy for the "might want SET NULL" relationships** (`equipment.category_id`/`department_owner_id`/`current_location_id`) — RESTRICT (safe default, matches current behavior) or SET NULL (allows deleting a category/department/location even while equipment references it, orphaning the reference to NULL)? This is a business-rule call PR15B should not make unilaterally.
2. **Target index-naming convention** — standardize everything onto `ix_`/`uq_` (SQLAlchemy's default, matches the majority of existing indexes) or onto a more descriptive scheme? Recommend `ix_`/`uq_` for consistency with the majority and zero new convention to document, but flagging as an explicit choice rather than assuming it.
