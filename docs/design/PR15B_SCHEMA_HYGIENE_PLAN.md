## 3. Timezone Policy

### 3.1 Python

**Policy: use `datetime.now(timezone.utc)` everywhere a Python-side UTC "now" value is needed.** `datetime.utcnow()` returns a **naive** datetime that silently claims no timezone while implicitly meaning UTC — a footgun the instant it is compared against, or stored alongside, a timezone-*aware* value (which is exactly the mixed state this codebase is in today, per §3.3). `datetime.now(timezone.utc)` returns the identical instant, explicitly labeled, and is safe to compare/store/serialize alongside any other aware value without ambiguity. This is why Python's own documentation now recommends against `utcnow()`/`utcfromtimestamp()`.

### 3.4 Conversion expression and historical-data interpretation

**What `timestamp without time zone` technically is, stated precisely before discussing conversion:** a naive `timestamp` column stores a wall-clock date/time value — year, month, day, hour, minute, second — with no timezone semantics attached at all. PostgreSQL does not associate any zone or offset with it, and does not itself know what real-world instant, if any, that wall-clock value is meant to represent; that association exists only in the application code that wrote and reads the value, if it exists at all.

For the five columns converting in this migration, that association is known and traceable, not assumed: every stored value was written by `datetime.utcnow()` (confirmed — no other write path exists for any of them, see §3.2's call-site citations), and `datetime.utcnow()`'s documented behavior is to return the current wall-clock date/time expressed in UTC. So for these five columns specifically, the stored wall-clock value and the UTC wall-clock representation of the actual instant are, by construction, the same numbers — a fact about the write path, not an interpretation applied to the data afterward. The correct, meaning-preserving conversion is therefore:

```sql
ALTER TABLE audit_logs
  ALTER COLUMN created_at TYPE timestamptz
  USING created_at AT TIME ZONE 'UTC';
```

repeated per column/table. `AT TIME ZONE 'UTC'` does not change the wall-clock numbers stored in any existing row, and does not apply a new interpretation to them — it takes the wall-clock value exactly as stored and declares, explicitly, that this wall-clock value is to be read as a UTC wall-clock value, which for these five columns is already what the write path (`datetime.utcnow()`, per §3.2) produced. The expression's role is purely mechanical: it closes the gap between what the write path always produced and what the column's own type has, until now, failed to declare, without touching the underlying numbers. This is explicitly **not** the same operation as `created_at::timestamptz` (a bare cast), which does not declare a known zone at all — it asks PostgreSQL to apply the database session's *current* timezone setting instead, which may or may not be UTC and is not tied to how the value was actually written. A bare cast would be an unsupported assumption about these five columns' meaning, exactly the kind of gap that has no evidence behind it for `due_at` (§3.4a); `AT TIME ZONE 'UTC'` avoids that gap here specifically because the write-path evidence already exists. This distinction must appear verbatim in the migration's own comments, not just this design document, to prevent a future maintainer from "simplifying" the expression into a bare cast.

**Downgrade expression (the exact inverse, stated explicitly per the cross-check requirement):**

```sql
ALTER TABLE audit_logs
  ALTER COLUMN created_at TYPE timestamp
  USING created_at AT TIME ZONE 'UTC';
```

repeated per column/table. Applied to an already-`timestamptz` value, `AT TIME ZONE 'UTC'` converts it to a naive value representing the same instant expressed in UTC wall-clock terms — the exact inverse of the upgrade expression, and lossless for the stored instant (see §3.6 for the forward-compatibility caveat this reversal does *not* eliminate).

### 3.4a Historical `due_at` — why it is excluded, and why that is not a gap (revised this round)

The prior round of this document lumped `borrow_transactions.due_at` in with the other five naive columns and applied the same "always UTC, safe to reinterpret" reasoning to it. **That was a factual error, corrected here.** The distinction matters and is worth stating precisely:

- **Where the other five columns' values come from:** every existing row's value in `audit_logs.created_at`, `notifications.created_at`, `equipment_status_history.changed_at`, `borrow_transactions.borrowed_at`, and `.returned_at` was written by this application's own server-side code calling `datetime.utcnow()` — traced to specific call sites (§3.2). The server controls the clock and the code; "this was always UTC" is a verifiable fact about that code path, not an assumption.
- **Where `due_at`'s values come from:** `git show 206d823:backend/app/schemas/transaction.py` (the commit immediately before Roadmap PR7a's lifecycle-model change) shows the pre-PR7a `BorrowRequest.due_at` was declared as a plain `datetime | None` field on the API request schema — accepted verbatim from whatever the caller (the desktop-era client, or an early version of the web frontend) sent, with **no server-side timezone normalization, validation, or default applied at write time.** The server never decided this value; a client did, and nothing in the code proves what timezone assumption that client made. Roadmap PR7a/7b then removed `due_at` from the write path entirely (§3.2), so there is no code path left to even inspect for a pattern — only the historical rows remain, with unknowable provenance.

**Because there is no evidence — not "weak evidence," genuinely none — for what timezone any given historical `due_at` value was expressed in, `AT TIME ZONE 'UTC'` cannot be asserted for this column the way it can for the other five.** Applying it anyway would silently manufacture a specific interpretation (UTC) for data that might have been entered in Bangkok local time (ICT, UTC+7) by hospital staff using an old client, or in whatever timezone a since-decommissioned system assumed — this document has no way to know, and neither would the migration.

**Resolution: PR15B does not convert `due_at`'s column type and does not reinterpret its existing values in any way.** It remains `timestamp without time zone` (naive), completely untouched by Migration A. This is not a hygiene gap left unaddressed by oversight — it is a deliberate decision that the column's dead write path (§3.2) means there is no live bug to fix (Option A's whole purpose — preventing *future* naive-timestamp writes — has nothing to protect here, since nothing writes to this column anymore) and no way to safely correct historical meaning without fabricating a fact this document cannot support. If the due-date workflow is ever revived in a future Roadmap PR, that PR is where `due_at`'s timezone semantics get defined and enforced going forward — new rows can and should get a proper `timestamptz` treatment at that time — but it must not retroactively assume a timezone for the rows that already exist under the old, unconstrained client-supplied contract. `report_service.py`'s CSV/XLSX export, which reads `due_at` directly for historical reporting, continues to emit exactly what is stored, with no timezone claim attached, exactly as it does today.

### 3.5 The `TimestampMixin`-inconsistency question (new in this round)

Four of the six naive columns (`audit_logs.created_at`, `notifications.created_at`, `equipment_status_history.changed_at`, `borrow_transactions.borrowed_at`) are all conceptually "row creation timestamp" columns — the exact same job `TimestampMixin.created_at` already does correctly (`DateTime(timezone=True)` + `server_default=func.now()`). Today these four instead use a bespoke `mapped_column(default=datetime.utcnow, nullable=False)` definition, meaning the codebase currently has **two different mechanisms** computing the same conceptual value. Two remediation options, presented for architecture approval rather than decided unilaterally:

- **Option A (approved, lower risk): fix the type only.** Convert the database column type to `timestamptz` (§3.4) and change the Python-side default callable from `datetime.utcnow` to `lambda: datetime.now(timezone.utc)` — the column becomes correctly aware, the value becomes correctly labeled, but the *computation mechanism* (Python decides the value, before `INSERT`) is unchanged. This is the narrowest possible fix: one column-type ALTER, one one-line callable change per column, no change to who computes the value or when.

  **Required accompanying ORM change (new this round, same class of gap as §4/§6.4):** confirmed via inspection (`app/models/audit.py:28`, `notification.py:24`, `equipment.py:202`, `transaction.py:142,151`) that all five converting columns are declared as bare `mapped_column(default=datetime.utcnow, nullable=False, ...)` with **no explicit `DateTime(...)` type argument** — SQLAlchemy infers a plain, naive `DateTime()` from the `Mapped[datetime]` annotation alone. Migration A must be paired with adding an explicit `DateTime(timezone=True)` type argument to all five `mapped_column()` declarations (mirroring exactly how `TimestampMixin` already does it). Without this, `Base.metadata.create_all()` — migration `0001_initial.py`'s bootstrap mechanism, and the SQLite test suite's schema source — would keep producing a naive column indefinitely, even after Migration A ships, diverging from the post-migration PostgreSQL catalog. This is the same "migration + ORM model change bundled together" requirement already established for FK `ondelete` (§4) and index/constraint naming (§6.4), now closed for the timezone conversion too. See §8.7/§8.7a for why this specific fix also changes what a *fresh* install looks like.
- **Option B (further consistency, not recommended for this pass without explicit sign-off): converge onto `TimestampMixin`'s pattern.** Replace the bespoke `default=datetime.utcnow` with `server_default=func.now()`, matching `TimestampMixin` exactly, eliminating the two-mechanism inconsistency entirely. This is a genuine (if narrow) behavior change: the value is now computed by PostgreSQL at `INSERT` time rather than by Python immediately before it, which is marginally more correct (immune to any application-clock skew) but is a different code path than what these four columns have used since they were introduced, and would need its own regression coverage proving no observable ordering/`after`-payload/test-fixture regression across `audit_logs`, `notifications`, `equipment_status_history`, and `borrow_transactions.borrowed_at` consumers.

**Option A is the approved choice for PR15B** (confirmed via the PR #52 review); Option B remains a documented future refinement (§9 item 2), not adopted now — consistent with the instruction to avoid introducing unapproved behavior changes and to keep this pass minimal-risk.

### 3.6 Rollback limitations

Downgrading `timestamptz` back to `timestamp` (`... USING created_at AT TIME ZONE 'UTC'`, the inverse expression) is lossless for the *value* (the same UTC instant, re-stripped of its label) but is **not** risk-free going forward: any code deployed against the timestamptz schema that started relying on timezone-aware comparison semantics would silently regress to naive-comparison behavior after a downgrade. This must be stated explicitly in the migration's downgrade docstring (matching the established pattern in migration `0004`'s downgrade docstring on destructive-vs-non-destructive framing), not presented as a risk-free revert.

### 3.7 Required testing

Per the explicit instruction, this is not treated as a mechanical replacement:

1. **Fresh database (revised this round — see §8.7a):** `base → 0012` produces the target `timestamptz` schema for all five converting columns. This is no longer asserted as "no intermediate naive state ever materializing" as an unconditional guarantee — it is the *result* of Migration A's verify-and-no-op check (§8.7a): once the accompanying ORM `DateTime(timezone=True)` fix (§3.5) lands, `0001` already produces `timestamptz` directly and Migration A no-ops per column; test both that a fresh install reaches the target schema and that Migration A's no-op path does not re-run the `AT TIME ZONE 'UTC'` conversion against an already-aware column (§8.7a's data-corruption warning).
2. **Historical upgrade** — rehearse against a database seeded with rows at the pre-`0012` baseline containing real historical values (not empty tables), proving the `AT TIME ZONE 'UTC'` conversion preserves the exact instant for pre-existing data.
3. **Downgrade** — prove the reverse conversion is lossless for the stored instant, and that the downgrade docstring's caveat (§3.6) is accurate.
4. **Re-upgrade** — the same round-trip discipline every migration since `0004` has followed.
5. **SQLite parity** — the non-PostgreSQL test suite (`Base.metadata.create_all()`) does not enforce `timestamptz` the way PostgreSQL does; confirm the ORM-level `DateTime(timezone=True)` type still round-trips correctly through SQLite's storage (SQLAlchemy's SQLite dialect stores aware datetimes as ISO strings and can lose `tzinfo` on read-back unless handled carefully), so the two dialects' test suites don't silently diverge in what they actually verify.
6. **PostgreSQL parity** — the equivalent PostgreSQL-marked assertions confirming the column is genuinely `timestamptz` at the catalog level (`information_schema.columns.data_type`), not just "the ORM object has tzinfo," which SQLite could satisfy without the underlying column enforcing anything.
7. **Serialization** — confirm FastAPI/Pydantic response serialization of the now-aware datetimes produces the shape frontend code actually consumes. This is a concrete, user-visible finding from this round's investigation, not a theoretical concern: `frontend/src/pages/EquipmentDetailPage.tsx` and `ReturnPage.tsx` call `new Date(tx.borrowed_at)`, `new Date(tx.returned_at)`, and `new Date(h.changed_at)` directly on the API response strings and render them via `.toLocaleString("th-TH")`. Today, because these values serialize with **no UTC offset** (naive), the browser's `Date` parser interprets them as **local time**, not UTC — a latent, currently-unverified display-correctness bug. After conversion, the same values serialize *with* an explicit `+00:00` offset, which `new Date(...)` parses correctly as UTC before `.toLocaleString()` converts it to the browser's local display timezone. This is a **user-visible improvement**, not a neutral wire-format detail — displayed dispatch/receipt/status-change times will shift by the local UTC offset amount (correcting them), and this must be verified explicitly against the frontend before merge, not assumed compatible.

**This policy explicitly rejects treating the timezone migration as a mechanical `datetime.utcnow()` → `datetime.now(timezone.utc)` find-and-replace.** The column-type change, the conversion-expression correctness, the `TimestampMixin`-consistency question (§3.5), and the serialization/display-correctness impact (§3.7.7) are all first-class design concerns addressed before any implementation.

## 4. FK Policy

**Default policy: `RESTRICT` for every FK, unless a specific relationship's business workflow explicitly requires otherwise — and no such requirement has been approved for any relationship today.**

Verified via a live rehearsal: all 25 foreign keys currently use PostgreSQL's implicit `NO ACTION` (`pg_constraint.confdeltype = 'a'`). `NO ACTION` and `RESTRICT` are functionally identical for every FK in this schema today, because none of them is declared `DEFERRABLE` — the only difference between the two (deferring the check to end-of-transaction vs. checking immediately) only matters for deferrable constraints. Making `RESTRICT` explicit is therefore a documentation/intent clarification with **zero observable behavior change**, confirmed further by the fact that the running application has exactly one `DELETE` endpoint in its entire API (`DELETE /equipment/{id}`), and it performs a **soft** delete (`equipment_crud.soft_delete`, setting `deleted_at`) — it never issues a real SQL `DELETE`, so no FK's `ondelete` behavior is ever actually exercised by any code path today.

**Why `SET NULL` is not adopted by default for the three nullable columns under review (`equipment.category_id`/`.department_owner_id`/`.current_location_id`):** `SET NULL` is only a safe default when something in the business workflow actually depends on the reference silently clearing itself when the referenced row disappears — no such workflow exists here today. There is no confirmed deletion workflow for `equipment_categories`, `departments`, or `locations` at all (no `DELETE` route exists for any of the three), so proposing `SET NULL` now would be speculative schema design against a use case that has not been approved, not a response to an actual business rule. `RESTRICT` is the conservative choice precisely because it fails loudly (blocks the delete) rather than silently corrupting equipment records with an unexplained `NULL` the moment such a delete route is ever added — an operator would then have to trace *why* a piece of equipment lost its category/department/location after the fact. If a deletion workflow for master-data rows is ever approved, `SET NULL` can be adopted deliberately at that time, scoped to that workflow's actual requirements, rather than pre-emptively.

**Cross-check: ORM `ForeignKey(ondelete=...)` alignment (new finding, required by this round's review preparation).** Confirmed via `grep -rn "ForeignKey(" backend/app/models/*.py`: **none of the 25 `ForeignKey()` declarations in the ORM models currently specify an `ondelete=` parameter.** This matters beyond documentation-only concerns because migration `0001_initial.py` bootstraps its entire schema via `Base.metadata.create_all(bind=bind)` (confirmed at `alembic/versions/0001_initial.py:26`) — meaning the ORM model *is* the DDL source of truth for how FKs get created, not just a description of them. More critically, `backend/tests/conftest.py:28` (`await conn.run_sync(Base.metadata.create_all)`) builds the SQLite test database directly from ORM metadata, **bypassing Alembic migrations entirely**. If migration `0012`/`0013` adds `ON DELETE RESTRICT` to the PostgreSQL catalog via raw `ALTER TABLE ... DROP CONSTRAINT ... ADD CONSTRAINT ...` SQL without also updating the ORM `ForeignKey()` declarations to `ondelete="RESTRICT"`, two problems follow: (1) the SQLite test suite would continue running against FKs with no explicit `ondelete` semantics, silently diverging from what PostgreSQL actually enforces after the migration — the exact "current ORM metadata will produce the same schema as upgraded databases" cross-check this document is required to verify, and today it does **not**, absent this fix; (2) a future `alembic revision --autogenerate` would detect a spurious diff (ORM says `NO ACTION`, database says `RESTRICT`) and attempt to "fix" it by reverting the database back to `NO ACTION`, silently undoing this migration's intent. **Required fix, folded into the FK migration itself (not a separate step):** every one of the 25 `ForeignKey("...")` declarations in `app/models/*.py` must be updated in the same change to `ForeignKey("...", ondelete="RESTRICT")` — `RESTRICT` for all 25, including the three columns discussed below, per the approved decision (§9 item 1) — so ORM metadata, SQLite test schema, and the PostgreSQL catalog all converge on an identical, explicit policy. ## 6. Index Naming Plan

**Adopted convention:** `ix_<table>_<column>` for single-column indexes, `ix_<table>_<purpose>` for indexes not tied to one column's raw name (e.g. the trigram GIN indexes), `ix_<table>_<column1>_<column2>` for composite indexes — matching SQLAlchemy's own default naming, which already produces 29 of the schema's 64 indexes today. `uq_<table>_<column>` for named unique constraints, matching the 4 that already exist from PR10's provenance tables.

| Group | Count | Naming today | Example |
|---|---|---|---|
| SQLAlchemy-default indexes | 29 | `ix_<table>_<column>` (already correct) | `ix_equipment_bcm_code` |
| Named unique constraints | 4 | `uq_<table>_<columns>` (already correct) | `uq_confirmed_role_ownership_revision_name` |

**Note the two distinct SQL mechanisms required**, both metadata-only, both zero-rebuild, but not interchangeable: `ALTER INDEX ... RENAME TO ...` for plain/GIN indexes; `ALTER TABLE ... RENAME CONSTRAINT ... TO ...` for the 7 unique-constraint-backed indexes (PostgreSQL automatically renames the backing index when the owning constraint is renamed — attempting `ALTER INDEX` directly on a constraint-backed index name works too, but renaming the *constraint* is the correct, self-documenting operation since the constraint is the actual schema object with business meaning).

**Primary keys (`_pkey`) and their own PostgreSQL default naming are explicitly out of scope for this rename** — `_pkey` is PostgreSQL's own universal convention, not an inconsistency with anything else in this schema, and renaming primary keys carries a materially different risk profile (every FK in the schema references a primary key by object identity, not by name, so this is technically safe, but is unnecessary churn with zero naming-inconsistency to justify it).

### 6.3 Requirements (from the explicit instruction)

- **Metadata rename where possible:** 100% of this plan is `ALTER INDEX`/`ALTER TABLE ... RENAME CONSTRAINT` — no index is dropped and recreated.
- **No unnecessary rebuild:** confirmed zero rebuild for all 12 renames above; verified this is the correct PostgreSQL behavior (renaming an index or a constraint does not touch its underlying B-tree/GIN storage).
- **Verify names before rename:** the migration's `upgrade()` must query `pg_indexes`/`pg_constraint` for the *current* name before issuing the rename, exactly as migration `0011`'s `_ensure_index_concurrently()` already established the precedent of inspecting catalog state before acting rather than assuming a name exists.
- **Verify-and-no-op, not blind fail-closed (revised this round — see §8.7a/§8.7b for the full policy):** if the old name is not found, that is not automatically an error — the migration must next check whether the *target* name already exists (the fresh-install-after-ORM-fix case, §6.4/§8.7) **and, if so, that its full definition matches per §8.7b's semantic check**, not merely that the name matches. A target name found with a mismatched definition is not a no-op — it is §8.7c's mixed-state case. Only if the old name is absent, the target name is also absent, does the migration raise a clear `RuntimeError` naming the specific mismatch, matching the `_ensure_index_concurrently()`/migration-`0005`-`_preflight()` precedent of failing loudly with an actionable message rather than silently skipping or letting PostgreSQL's own (much less clear) error surface.
- **Fresh/historical convergence:** a fresh `base → 0014` install and a historical `0011 → 0014` upgrade must produce byte-identical final index/constraint names, verified as an automated regression test (same discipline every schema-bearing migration since `0004` has followed). (Corrected this round: the rename migration is `0014`, not `0012` — `0012` is the timezone migration per §8.2's three-migration split; this subsection previously cited the wrong migration number.)

### 6.4 Convergence: ORM metadata, immutable historical migrations, upgraded databases, fresh databases (new dedicated section this round)

§6.3's fresh/historical convergence requirement is necessary but not sufficient on its own — it proves the *database* ends up the same either way. This subsection addresses a layer above that: whether the **ORM model layer** (`app/models/*.py`, i.e. `Base.metadata`) itself agrees with what Migration C produces, since ORM metadata is what a direct `Base.metadata.create_all()` call uses (migration `0001_initial.py`'s bootstrap, and `tests/conftest.py:28`'s SQLite test setup — the same class of gap identified for FK `ondelete` in §4's cross-check).

**Root cause, confirmed by inspection:** `backend/app/db/base.py`'s `Base` declares no `MetaData(naming_convention={...})`. Without one, SQLAlchemy and PostgreSQL each apply their own independent defaults when a constraint/index has no explicit name — which is exactly why three different naming patterns exist today (§6.1). This has a direct consequence for convergence:

- **The 29 `ix_`-prefixed indexes and 4 named `uq_`-prefixed constraints** are already explicitly named in the ORM model layer (`index=True` triggers SQLAlchemy's own hardcoded `ix_<table>_<column>` default, and the 4 `uq_` ones from PR10 carry an explicit `UniqueConstraint(name=...)`). These are stable and require no further ORM change — `Base.metadata.create_all()` already produces the same names Migration C expects to already exist.
- **The 5 hand-named `idx_`-prefixed indexes** (4 GIN trigram, 1 partial unique) are **not declared anywhere in the ORM model layer at all** — confirmed via grep, they exist only as raw `op.execute("CREATE INDEX ...")` statements inside migrations `0001`, `0004`, and `0007`. This means `Base.metadata.create_all()` (and therefore the SQLite test suite) **never creates these five indexes, today or after this proposal** — a pre-existing asymmetry this proposal does not introduce and is not in scope to fix. It matters for one of these five specifically: `idx_tx_one_active_borrow` is not just a performance index, it is the real database-level guard against double-dispatching the same equipment (a genuine **safety index** — the invariant "at most one active borrow per equipment" is enforced by this partial unique index at the PostgreSQL level). Because it does not exist in ORM metadata, the SQLite test suite enforces that same invariant only through application-service logic, not the schema — already true today, unaffected by renaming it to `ix_borrow_transactions_one_active_borrow` in Migration C. **Renaming a safety index changes nothing about the invariant it enforces**; the constraint's protective role is orthogonal to its name, verified by testing that a duplicate-active-borrow attempt is still rejected after the rename, exactly as before.
- **The 7 auto-named `<table>_<column>_key` unique constraints** (§6.1) **are** declared in the ORM model layer (`unique=True` on the column), so `Base.metadata.create_all()` does create them — but since they carry no explicit name, PostgreSQL and SQLite each apply their own independent default naming, and neither matches Migration C's target `uq_<table>_<column>`. **This is the actual convergence gap for index naming, paralleling §4's FK finding exactly:** renaming the constraint at the database level via Migration C's `ALTER TABLE ... RENAME CONSTRAINT` does not change what `Base.metadata.create_all()` produces on a database Migration C never touched (SQLite tests). **Required fix, bundled into Migration C:** each of the 7 affected columns' `unique=True` must gain an explicit name — either `UniqueConstraint("<column>", name="uq_<table>_<column>")` replacing the bare `unique=True`, or a `MetaData(naming_convention={"uq": "uq_%(table_name)s_%(column_0_name)s", ...})` added to `Base` covering all constraint types at once. Either approach makes ORM metadata agree with the post-Migration-C PostgreSQL catalog **and** with what the SQLite test suite creates, closing the same class of gap identified for FK `ondelete=` in §4.

**Convergence summary across all four surfaces, post-Migration-C:**

| Surface | `ix_` (29) | `uq_` named (4, pre-existing) | `idx_`→`ix_` renamed (5) | `_key`→`uq_` renamed (7) |
|---|---|---|---|---|
| ORM metadata (`Base.metadata.create_all()`) | Matches | Matches | **Not present at all** (pre-existing, out of scope) | Matches, *if* the required fix above lands |
| Immutable historical migrations (`0001`–`0011`, never modified) | Produce today's pre-rename names, as they always have | Produce today's names, unchanged | Produce today's `idx_` names, unchanged | Produce today's `_key` names, unchanged |
| Upgraded database (`0011 → head`) | Unaffected (already `ix_`) | Unaffected (already `uq_`) | Renamed to `ix_` by Migration C | Renamed to `uq_` by Migration C |
| Fresh database (`base → head`), **before** the §6.4 ORM name fix lands | `ix_` from `0001` onward | `uq_` from their introducing migration onward | `idx_` created by `0001`/`0004`/`0007` (these 5 have no ORM declaration at all — see the bullet above — so this row is unconditional, not fix-dependent); Migration C finds the old name and transforms it (§8.7a outcome 1) | `_key` created implicitly by unnamed `unique=True`; Migration C finds the old name and transforms it (§8.7a outcome 1) |
| Fresh database (`base → head`), **after** the §6.4 ORM name fix lands | `ix_` from `0001` onward | `uq_` from their introducing migration onward | Unchanged — still `idx_` created by `0001`/`0004`/`0007` regardless of the ORM fix (no ORM declaration exists to fix); Migration C still transforms (outcome 1) | `0001` already creates `uq_<table>_<column>` directly (the ORM fix is exactly what makes this so); Migration C finds the target name already present and no-ops (§8.7a outcome 2) |

Both database paths converge on the same final names (every column above ends at `ix_`/`uq_` regardless of row) precisely because Migration C never assumes a name — it inspects `pg_indexes`/`pg_constraint` immediately before renaming (§6.3/§8.7a's three-way check) and acts on whatever it actually finds: transforms if it finds the old name, no-ops if it already finds the target name, and fails closed only if it finds neither (§8.7c below covers the case where it finds *both*, or finds the target name with the wrong definition).

## 8. Migration Plan

**Migration numbering begins at `0012`** — confirmed baseline migration is `0011_pagination_ordering_indexes` (no migration has been added since; PR15A shipped zero schema changes), giving a planned implementation sequence of `0012`–`0014` and a planned design head of `0014`. **No existing migration file is modified.**

### 8.1 Validate-before-enforce strategy

Every constraint or type change in PR15B follows the pattern migration `0005` already established (`_preflight()`: a validation query proving existing data already satisfies the new rule, raising a clear, actionable `RuntimeError` naming offending rows if it does not, *before* the schema-altering statement runs — never letting `ALTER TABLE ... ADD CONSTRAINT`/`ALTER COLUMN ... TYPE` itself fail with an opaque PostgreSQL error). Concretely for PR15B:

- **Timezone conversion** does not require a data-validation preflight in the traditional sense (there is no "row that violates the new type" the way a CHECK constraint can be violated — every naive value converts unambiguously per §3.4), but it does require the §8.7a catalog-*type* check (`information_schema.columns.data_type` — already `timestamptz`, or still naive) before deciding whether to alter at all, plus verification that the `AT TIME ZONE 'UTC'` expression will not silently produce a NULL or error for any existing row on the columns that do need transforming (e.g., confirm no column has a sentinel/out-of-range value that would behave unexpectedly under the conversion).
- **FK `ondelete` changes** require no *data* preflight — no existing row can violate a delete-behavior change, since the change only affects what happens on a future `DELETE` that has never occurred (§4) — but do require the full §8.7a/§8.7b semantic catalog-state check (`confdeltype` as a first-pass filter, then the complete FK-definition comparison) to decide transform vs. no-op vs. §8.7c's mixed-state case.
- **Index/constraint renames** require a name-existence preflight (§6.3/§8.7a's three-way check), not a data-validation preflight.

### 8.2 Upgrade strategy — approved: three separate migrations, not one combined migration

PR15B ships as **three independently-revertible migrations**, approved via the PR #52 review, rather than one combined `0012_schema_hygiene.py` (the combined approach considered in an earlier round of this document is superseded by this decision; see §9 item 3 for the reasoning that led to it):

- **Migration A — `0012_timezone_conversion.py`**: the **five** naive-column `timestamptz` conversions (§3.4, Option A per §3.5) — `audit_logs.created_at`, `notifications.created_at`, `equipment_status_history.changed_at`, `borrow_transactions.borrowed_at`, `.returned_at`. `borrow_transactions.due_at` is explicitly **not** part of this migration (§3.4a) — it remains naive, untouched. Migration A also carries the three accompanying Python call-site fixes (`auth_service.py::last_login_at`, `crud/transaction.py::returned_at`, `crud/equipment.py::soft_delete()::deleted_at` — none of these three require a migration on their own, only a code change bundled with this one since they fix the same class of bug the migration addresses).
- **Migration B — `0013_fk_ondelete_policy.py`**: explicit `ondelete="RESTRICT"` on all 25 FKs (§9 item 1), bundled with the corresponding 25 `ForeignKey(ondelete=...)` ORM model updates (§4 cross-check) so the migration and the model change land atomically.
- **Migration C — `0014_index_naming_convergence.py`**: the 12 index/constraint renames (§6.2).
- The `Notification.type` stale-comment fix and `docs/TECH_DEBT.md` TD-001 status correction are documentation/comment-only and require no migration; they can accompany whichever of A/B/C is judged most relevant to review together, or ship as their own trivial documentation commit.

**Notation used from this point forward:** "head" means `0014` — the state after all three of Migrations A/B/C have applied. Where this document instead refers to a single migration's own isolated test (e.g. Migration A alone), it names that migration's specific number (`0012`) rather than "head."

**Why separation reduces risk and simplifies rollback, versus one combined migration:**
- **Independent revert:** if the timezone conversion (Migration A) needs a downgrade for any reason (e.g., an unforeseen SQLite-parity or frontend-serialization issue caught late), Migrations B and C — which touch entirely unrelated schema concerns — are not forced to revert with it. A single combined migration makes every downgrade all-or-nothing.
- **Narrower blast radius per review:** each migration's `upgrade()`/`downgrade()` pair is reviewable and testable in isolation against its own concern (timezone semantics vs. FK delete behavior vs. cosmetic renames), rather than one large diff mixing three unrelated risk profiles (§10 already separates these into High/Medium/Low — the migration structure should mirror that separation).
- **Clearer historical-upgrade testing:** the required fresh/historical/downgrade/re-upgrade rehearsal (§8.5) is simpler to reason about and to write regression tests for when each migration has one concern, rather than asserting compound before/after state across three unrelated changes in one file.
- **Precedent-consistent, not precedent-breaking:** migrations `0005`/`0006`/`0009` bundled several *closely related* sub-changes serving one coherent Roadmap PR concern (e.g., `0006`'s status-model collapse). PR15B's three concerns (timezone, FK policy, index naming) are not sub-parts of one coherent change the way those were — they are three independent hygiene concerns that happen to share a Roadmap PR number, which is a materially different case for bundling.

All three migrations are still scoped strictly to PR15B and still begin numbering at `0012` (baseline migration: `0011_pagination_ordering_indexes`; planned design head: `0014`).

### 8.7 Catalog-aware migration strategy: fresh database vs. historical upgrade (expanded this round)

§8.5 stated the fresh/historical rehearsal requirement briefly; this section spells out the two paths explicitly, why they can diverge if a migration is written carelessly, and where each of Migrations A/B/C must inspect actual catalog state rather than assume it.

**This document specifies exactly one authoritative migration strategy, applied identically regardless of which path a given database happens to be on.** Both paths below are described using the same verification-first model — neither path "skips verification" or follows any separate, unverified route. The only thing that differs between them is what the *first* catalog inspection typically finds, not whether inspection happens.

**Fresh database.** `0001_initial.py` creates schema via `Base.metadata.create_all(bind=bind)` from **current** ORM metadata — whatever `app/models/*.py` declares at the moment the fresh install runs, not a fixed historical snapshot frozen at `0001`'s authoring time. Migrations `0002`–`0011` then apply their own changes, and finally Migrations A/B/C (`0012`–`0014`) run. For each object those migrations touch, they:

1. **Inspect the PostgreSQL catalog** (`information_schema.columns`, `pg_constraint`, `pg_indexes`/`pg_index`) for that object's actual current state — never assumed.
2. **Verify the complete target definition and object health** (§8.7b's semantic equivalence check, extended in this round to include index health state — `indisvalid`/`indisready` — not merely name/type/definition).
3. **Perform an intentional no-op only when the target state is semantically correct *and* healthy.** Once this proposal's required ORM changes land (`DateTime(timezone=True)` §3.5, `ForeignKey(ondelete=...)` §4, explicit constraint names §6.4), `0001`'s `create_all()` produces the target schema directly for most objects, so step 2 typically finds them already correct and step 3 is reached immediately. This is not a separate path with weaker guarantees — it is the same three-step inspect/verify/act sequence, just one where the transformation in step 3 usually turns out to be unnecessary.

**Historical database.** An existing, already-deployed PostgreSQL database sitting at baseline migration `0011` runs `alembic upgrade head` (moving it to the planned design head, `0014`) and executes only Migrations A/B/C. Its schema is the real, currently-running production (or production-like) schema, accumulated over however long the deployment has been live — not transient, not assumed pristine. For each object, the migrations:

1. **Inspect the current catalog state** — the same query as the fresh-database path, no different mechanism.
2. **Verify the expected legacy (pre-migration) definition** — confirming the object is genuinely in the state this proposal expects to transform (naive `timestamp`; implicit `NO ACTION`; the old name), not merely assuming it because this is "the historical path."
3. **Perform the approved transformation** — §3.4's `AT TIME ZONE 'UTC'` ALTER, §4's constraint replacement, or §6.2's rename, exactly as designed.
4. **Verify the complete target definition and object health afterward** — the same post-condition check the fresh-database path performs when it finds the target state already present in step 2. This closes the loop: both paths are checked against the identical target definition, whether that definition was already present or was just produced by step 3's transformation.

**Any state that is mixed, incomplete, invalid, or otherwise unexpected on either path fails closed** — §8.7c specifies the exact scenarios (mismatched definition, both legacy and target objects present, and — new this round — a correctly-named-and-defined-but-unhealthy index) and the required stop-and-report behavior. There is no wording anywhere in this design that permits either path to proceed past an object that fails verification.

**Why both paths converge to the identical, healthy target schema:**
- **Timezone (Migration A):** both paths end with the same five columns as `timestamptz`, verified via the post-condition check in step 3 (fresh) / step 4 (historical) above — not assumed from which path was taken. The `USING ... AT TIME ZONE 'UTC'` expression (§3.4) produces the same output type and the same value-preserving semantics regardless of which path's catalog inspection found the naive "before" value. `due_at` is excluded from conversion on *both* paths identically (§3.4a) — there is no path-dependent special case for it.
- **FK policy (Migration B):** both paths end with all 25 FKs carrying an explicit `ondelete` policy in the PostgreSQL catalog (`pg_constraint.confdeltype`, verified via §8.7b's full definition check) **and** in the ORM `ForeignKey(ondelete=...)` declarations (§4 cross-check) — the migration changes the database, the accompanying model-source change changes what a fresh `Base.metadata.create_all()` would produce. Because Migration B updates both simultaneously, there is no window where the two paths could disagree about the final `ondelete` value.
- **Index naming (Migration C):** this is the path where convergence needs the most explicit catalog inspection — see the dedicated §6.4 this round adds, which covers exactly this convergence question for index/constraint names specifically (ORM metadata, migration-only objects, and the `0014` rename all have to agree), and §8.7b's health-state extension, which ensures convergence includes not just naming and definition but also that the resulting index is actually usable by the query planner.

**Summary of the inspection requirement:** none of Migrations A/B/C may assume the name, type, constraint definition, or index health state their `upgrade()` logic expects — each must query `information_schema.columns` (types), `pg_constraint` (FK/CHECK definitions and current names), or `pg_indexes`/`pg_index` (index names, definitions, and health flags) for the *actual* current catalog state immediately before acting, on both paths, every time. §8.7a/§8.7b/§8.7c immediately below specify the full three-outcome classification (needs transformation / already at healthy target state / fails closed) this requires — the same underlying discipline migration `0011`'s `_ensure_index_concurrently()` and migration `0005`'s `_preflight()` established (§8.1, §6.3), extended to cover semantic definition and health, not just names.

### 8.7a Verify-and-no-op policy (resolves the fresh-install blocker; revised this round to require semantic verification, not name/type matching alone)

Each of Migrations A/B/C must classify the catalog state it finds for every object it touches into exactly one of three outcomes, not two:

1. **Needs transformation** — the object is in the pre-migration state (naive `timestamp`; implicit `NO ACTION`; the old auto-generated or `idx_`-prefixed name). The migration performs its transformation exactly as designed (§3.4's `AT TIME ZONE 'UTC'` ALTER; §4's constraint replacement; §6.2's rename).
2. **Already at target state** — the object's **complete definition, and, for indexes, its health state** (not merely its name or column type — see §8.7b immediately below for exactly what "complete" means for each object kind, extended this round to include `pg_index.indisvalid`/`indisready`) already matches what the migration exists to produce. This is the case §8.7's fresh-install correction identifies as newly possible: once the accompanying ORM model changes land, a fresh `0001`-driven install reaches this state without any of `0012`–`0014` doing anything. **The migration performs no schema rewrite and no destructive action — it verifies the full definition and health match the target, logs that it found nothing to do, and exits successfully.** This is an intentional, expected no-op, not a degraded or partial run.
3. **Neither** — the object is in some other, unrecognized state (wrong type entirely; a name matching the target but a definition that does not; a correctly-defined index that is not healthy — see §8.7c's mixed-state policy, which governs these cases specifically and takes precedence over the simple three-way framing here). This is the only outcome that raises a clear `RuntimeError` naming the specific mismatch — genuinely unexpected state, not merely "already done."

**Important — outcome 2 requires §8.7b's full semantic check, not just a name or type lookup.** A prior round of this document described outcome 2 in terms of `information_schema.columns.data_type` matching, `pg_constraint.confdeltype` matching, or a name matching — each of those is a *necessary* check but none of them is *sufficient* on its own to conclude "already at target state." §8.7b redefines exactly what must match for each object kind before a migration is permitted to call something outcome 2 rather than outcome 3.

**Concretely, per migration (summarized here; §8.7b has the full field-by-field detail):**

- **Migration A (timezone):** query `information_schema.columns.data_type` for each of the five converting columns. `timestamp without time zone` → transform (outcome 1). `timestamp with time zone` → proceed to §8.7b's semantic check before concluding outcome 2 — **and regardless of outcome, do NOT run the `AT TIME ZONE 'UTC'` `ALTER ... USING` expression against a column already `timestamptz`**: applying that conversion a second time does not raise an error, and its effect on the stored value is not a fixed, predictable one — the expression first renders the aware value as a naive UTC wall-clock representation, and the subsequent implicit cast back to `timestamptz` (required because the target column type is `timestamptz`) is then resolved using whatever timezone setting is in effect for the session running the migration. If that session's effective timezone happens to be UTC, the round-trip is harmless; if it is not, the value shifts by that session's offset. **The risk is exactly that this depends on session state the migration does not control and should not have to reason about — not that it always produces one specific wrong answer.** This is the single most important reason this section exists: verify-and-no-op removes the dependency on session timezone entirely, by never running the expression a second time in the first place, rather than relying on an assumption about what any given session's timezone will be.
- **Migration B (FK policy):** query `pg_constraint.confdeltype` for each of the 25 FKs as a first-pass filter, then §8.7b's full FK-definition comparison before concluding outcome 2. `a` (`NO ACTION`) → transform (outcome 1). A `confdeltype` matching the target, **with every other field of the constraint also matching** (§8.7b) → no-op (outcome 2). A `confdeltype` matching the target but any other field differing (e.g. it references the wrong column, or is unexpectedly `DEFERRABLE`) → §8.7c's mixed-state policy, not outcome 2. Any `confdeltype` this proposal never intends (`c` `CASCADE`, `d` `SET DEFAULT`) → outcome 3, fail closed.
- **Migration C (index naming):** query `pg_indexes`/`pg_constraint` for the **old** name first. Found → transform (rename), after confirming via §8.7b that the object found under the old name is in fact the object expected there (not, say, a same-named but differently-defined index from some other change). Old name not found → query for the **target** name — found, **its full definition matches per §8.7b, AND `indisvalid = true`/`indisready = true`** → no-op (outcome 2; the fresh-install-after-ORM-fix case for the 7 auto-named constraints, §6.4). Target name found but its definition does not match, or matches but is unhealthy → §8.7c's mixed-state policy (Scenario 2 or 3 respectively). Neither old nor target name found → outcome 3, fail closed.

**Why this is a genuine convergence guarantee, not just error-avoidance:** with the three-way check backed by semantic verification, Migrations A/B/C produce the identical end state whether they run against a database that needed transformation (the historical-upgrade path, or a fresh install predating the ORM fix) or a database that already had the target state (a fresh install post-ORM-fix) — the migration's *observable effect on the schema* is the same (target state reached, with a verified-correct definition) even though its *internal action* differed (transform vs. no-op). This is the concrete form of "both paths converge" that §8.7 asserts in the abstract.

### 8.7b Semantic equivalence verification (new this round — redefines what "already at target state" means)

Matching names, and matching a single summary field like a column's base type or an FK's `confdeltype`, are **necessary but not sufficient** to conclude an object is already at its target state. An object can carry the target name and still differ in a way that matters — a constraint renamed by some out-of-band process but never actually pointed at the right columns, for instance. **Verification must compare the complete object definition**, not a single attribute. For PR15B, "complete" means:

**Foreign keys (Migration B) — every one of the following must match, not `confdeltype` alone:**
- **Referenced table** (`pg_constraint.confrelid`) — the FK must point at the table this proposal's §4 table says it should (e.g. `equipment.category_id` → `equipment_categories.id`, not some other table).
- **Referenced column(s)** (`confkey`, resolved to column names) — for composite or renamed-column scenarios; every FK in this schema is single-column today (§4), but the check must still resolve and compare the actual column, not assume it.
- **Local column(s)** (`conkey`, resolved to column names) — the FK must originate from the column §4's table says it does.
- **`ON DELETE`** (`confdeltype`) — matches the approved policy: `RESTRICT` for all 25 FKs (§9 item 1).
- **`ON UPDATE`** (`confupdtype`) — this proposal never proposes anything other than the PostgreSQL default (`NO ACTION`/`a`) for `ON UPDATE`; a constraint found with any other `confupdtype` is a definition mismatch, not a match, even if `ON DELETE` is correct.
- **Deferrable state** (`condeferrable`, `condeferred`) — confirmed in §4 that no FK in this schema is deferrable today, and this proposal does not introduce deferrability; a constraint found as `DEFERRABLE` is a mismatch.
- **Validation state** (`convalidated`) — a constraint added as `NOT VALID` (unvalidated) is not equivalent to a fully validated one even if every other field matches; PR15B's constraints must be fully validated, matching the `_preflight()`-then-validate discipline of migration `0005` (§8.1).

The practical query is `pg_get_constraintdef(oid)` (returns the full, human-readable constraint definition PostgreSQL itself considers canonical) compared against the exact expected definition string, in addition to the individual `pg_constraint` columns above — comparing both the rendered definition and the underlying columns guards against a false match from string formatting differences masking a real semantic difference.

**Indexes and unique constraints (Migration C) — every one of the following must match, not the name alone — plus index health state, added this round:**
- **Expected name matches** and **expected table matches** — the baseline checks, insufficient alone.
- **Indexed column(s)**, in order — `idx_tx_one_active_borrow`'s rename target must still be indexing `equipment_id`, not some other column an out-of-band change substituted.
- **Uniqueness** — a unique index found under the target name that is not actually unique (or vice versa) is a mismatch, not a match — this is the difference between a real safety index and a decoy with the right name.
- **Key columns and expressions** (for the 4 GIN trigram indexes, which index `lower(<column>)`-style expressions, not bare columns) — the exact indexed expression must match, not just that *an* index with the target name exists on the right table.
- **Sort direction and null-ordering**, where applicable (`ASC`/`DESC`, `NULLS FIRST`/`NULLS LAST` per column) — this proposal's own indexes are single-column today, but the check must still confirm both rather than assume them, since these are exactly the kind of attribute a name match would hide a mismatch in.
- **Predicate** (for `idx_tx_one_active_borrow`'s partial-index `WHERE status = 'open'` clause) — a same-named index missing or altering this predicate would silently weaken the safety guarantee §6.4 describes; this must be checked explicitly, not assumed from the name.
- **Included columns**, where applicable (`INCLUDE (...)`, PostgreSQL 11+) — none of this schema's indexes use `INCLUDE` today, but the check must confirm absence, not assume it.
- **Collation** — an index built with a non-default collation is not equivalent to one built without, even on the same column.
- **Access method** (`pg_class.relam`, resolved via `pg_am` — e.g. `btree` vs. `gin`) — the 4 trigram indexes are `gin`; a same-named `btree` index on the same column is not the same object and must not be accepted as a match.
- **`pg_index.indisvalid = true`** — an index (or index-backed constraint) can exist in the catalog with the correct name and a byte-for-byte-correct definition and still be **invalid**: PostgreSQL leaves `indisvalid = false` on an index whose build was interrupted (a crashed or killed `CREATE INDEX CONCURRENTLY`, most commonly) or that failed a subsequent `REINDEX CONCURRENTLY`. An invalid index is not enforced by the planner for uniqueness/exclusion purposes and is not usable for query planning — it is present in the catalog but not actually doing its job.
- **`pg_index.indisready = true`** — distinct from `indisvalid`: `indisready = false` means the index is not yet receiving new-row updates at all (an even earlier point in a concurrent build that was interrupted before `indisvalid` would even become relevant). An index with `indisready = false` is even less "done" than one with `indisvalid = false`.

**An index or index-backed unique constraint that matches every definitional check above but has `indisvalid = false` or `indisready = false` is not a valid target-state object, full stop.** It must not be classified as outcome 2 (no-op) merely because its name and definition are otherwise correct — health state is a required, independent gate, not a tie-breaker for otherwise-ambiguous cases. See §8.7c's Scenario 3 for the required fail-closed handling: the migration must **not** silently no-op past it, and must **not** silently rebuild or drop it as a "fix," since the safe recovery action (typically `REINDEX CONCURRENTLY` or `DROP INDEX CONCURRENTLY` + recreate) depends on operational context (is a build currently in progress elsewhere? was this from a genuinely abandoned attempt?) this migration cannot determine on its own, and no such recovery strategy has been separately approved by this document.

The practical query is `pg_get_indexdef(indexrelid)` (the full, canonical index definition) compared against the exact expected definition, plus explicit checks of `pg_index.indisunique`/`indpred`/`indcollation`/`indisvalid`/`indisready` and `pg_class.relam` (via `pg_am.amname`) for the specific attributes above that a definition-string comparison alone might not make obvious to a human reviewer, or in the case of `indisvalid`/`indisready`/access method, might not appear in `pg_get_indexdef()`'s output at all.

**This is not optional rigor for its own sake — it is what makes outcome 2 (no-op) trustworthy rather than a guess.** A migration that concludes "already at target state" from a name match alone could silently accept a database that is subtly broken in a way that matters (an FK pointing at the wrong table with the right `ondelete`; an index on the wrong column with the right name) and report success. §8.7c below specifies what happens when this deeper check finds a mismatch.

### 8.7c Fail-closed mixed-state policy (three scenarios; Scenario 3 added this round)

Three specific catalog states are distinct from the ordinary three-way outcomes in §8.7a and require their own explicit handling, because each represents a genuinely ambiguous, contradictory, or unhealthy state that no migration should attempt to resolve automatically:

**Scenario 1 — both a legacy-named and a target-named object exist simultaneously.** For example, a database somehow has both `users_email_key` (the old auto-generated name) *and* `uq_users_email` already present — this should not happen under any normal upgrade or fresh-install path this proposal defines, and its existence indicates either a partially-applied prior migration attempt, manual intervention, or a genuinely unknown history for that database.

**Scenario 2 — an object under the target name exists, but its definition (per §8.7b's semantic check) does not match what this proposal expects.** For example, a constraint named `uq_users_email` exists, but it is not actually a unique constraint on `email` — perhaps it is unique on a different column, or not unique at all. The name alone would suggest outcome 2 (already done); the semantic check reveals it is not.

**Scenario 3 (new this round) — an index or index-backed constraint under the target name has a fully correct definition but is unhealthy: `pg_index.indisvalid = false` or `indisready = false`.** This is distinct from Scenario 2 because the *definition* is right — the object would be indistinguishable from a genuine target-state match by a name-plus-definition check alone. Only the health-state check (§8.7b's extension this round) reveals the problem. The most common real-world cause is an interrupted `CREATE INDEX CONCURRENTLY` or `REINDEX CONCURRENTLY` — a process killed, a connection dropped, or a deploy interrupted mid-build — leaving an index that exists, looks correct, but is not enforced by the planner and may not even be receiving row updates.

**In any of the three scenarios, the migration must:**
- **Stop** — halt `upgrade()` for that migration immediately, before making any further schema change in the same migration run.
- **Report the mismatch** — raise a `RuntimeError` (matching the established `_preflight()`/`_ensure_index_concurrently()` precedent, §8.1/§6.3) whose message states plainly which scenario was hit, which object(s) were found, and what their actual definitions and health flags are versus what was expected — enough detail for a human to diagnose the situation without re-deriving it from raw catalog queries. For Scenario 3 specifically, the message must include the actual `indisvalid`/`indisready` values found.
- **Require manual intervention** — the migration does **not** attempt to resolve the ambiguity or unhealthy state itself.

**Explicitly, the migration must never, under any of the three scenarios:**
- **Silently repair** — it must not assume the target-named-but-wrong-definition object (Scenario 2), or the unhealthy index (Scenario 3), should simply be corrected in place and proceed to do so; the existence of a wrong definition or an unhealthy index under the target name means something happened that this design did not anticipate, and guessing at the fix risks compounding whatever already went wrong.
- **Overwrite** — it must not drop and recreate the mismatched or unhealthy object to force it into the expected shape without an operator's explicit decision, since the object may be intentionally different for a reason this migration cannot know (Scenario 2), or a `DROP INDEX CONCURRENTLY` + recreate may race with an operation already in flight elsewhere (Scenario 3) — the safe recovery action for an unhealthy index depends on operational context this migration cannot determine on its own, and no such recovery strategy has been separately approved by this document.
- **Silently rebuild** — specific to Scenario 3: the migration must not issue its own `REINDEX`/`REINDEX CONCURRENTLY` as an automatic "fix" for an unhealthy index. A deterministic, approved recovery strategy for this case does not exist in this proposal; if one is wanted, it must be designed and approved separately, not improvised inline during Migration C.
- **Guess** — it must not pick one of the two legacy/target objects in Scenario 1 as "the real one" and proceed as if the other did not exist; both are real catalog objects and only a human with deployment-specific context can determine which (if either) is correct.

This policy is the same "fail loudly, do not paper over" discipline this document has applied throughout (§8.1's `_preflight()`, §6.3/§8.7a's name checks) — §8.7c exists to state explicitly that mixed, contradictory, or unhealthy states are handled by the *same* discipline, not silently absorbed into the ordinary no-op path just because a name (or even a full definition) happens to match.

### 8.7d Mandatory PostgreSQL regression test: interrupted/incomplete index build (new this round)

This is a required test, not merely a documented policy — Scenario 3 above must be proven to actually fail closed, not just described as doing so.

**Construction:** using a real PostgreSQL 16 instance (not SQLite — see below for why), construct a database state where, for the index Migration C is about to rename or verify:
- the target index name already exists in the catalog,
- its definition (via `pg_get_indexdef`) appears correct — same table, same columns, same predicate, same uniqueness,
- but `pg_index.indisvalid = false` or `indisready = false`.

The most direct construction technique is to start a `CREATE INDEX CONCURRENTLY` under the target name and kill the backend process (or the connection) partway through, which is exactly the real-world failure mode this scenario models — PostgreSQL leaves the partially-built index in the catalog in this unhealthy state rather than rolling it back automatically (unlike a normal, non-concurrent DDL statement). An equivalent, more deterministic alternative for test purposes is directly manipulating `pg_index.indisvalid`/`indisready` via a privileged test-only update, provided the test also documents that this is a simulation of the concurrent-build-interruption scenario, not a claim that application code would ever do this.

**Expected result, all of which the test must assert:**
- Migration C's preflight/verification step detects the unhealthy index before attempting any rename or replacement.
- The migration terminates (raises) rather than proceeding.
- No rename or replacement operation is issued against the unhealthy index — confirmed by asserting the index's name and definition are byte-for-byte unchanged after the failed migration attempt.
- No partial schema mutation is left behind anywhere else in the same migration run — confirmed by asserting every *other* object Migration C would have touched is also untouched (the whole migration aborts, not just the one problem object).
- The raised error's message identifies the specific unexpected catalog state — naming the index, and stating the actual `indisvalid`/`indisready` values found versus the healthy values expected.
- **A subsequent run of the same migration does not incorrectly classify the still-unhealthy index as target-state-complete** — re-running `alembic upgrade head` against the same (still broken) database must fail the same way again, not silently succeed because a shallower check only re-confirmed the name and definition without re-checking health.

**Why this must be a real-PostgreSQL test and cannot be satisfied by the SQLite suite:** `indisvalid`/`indisready` are PostgreSQL-specific catalog concepts tied to `CREATE INDEX CONCURRENTLY`'s multi-transaction build process — SQLite has no equivalent concurrent-index-build mechanism and therefore no equivalent unhealthy-index catalog state to construct. This scenario is `pytest.mark.postgres`-only, alongside the existing PostgreSQL-only evidence this document already requires (§8.6).

This test is required evidence for §11's acceptance criteria, alongside the existing fresh/historical/downgrade/re-upgrade rehearsal (§8.5) and the mixed-state tests already required for Scenarios 1 and 2 (§11).
