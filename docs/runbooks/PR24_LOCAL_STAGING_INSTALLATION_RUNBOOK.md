# คู่มือปฏิบัติงาน — Local Staging/UAT (PR24D-L1/L2/L3)

**Operator runbook — Medical Equipment Pool, Local Staging/UAT**

เอกสารนี้เป็นคู่มือหลักสำหรับผู้ดูแลระบบ (operator) ที่ติดตั้งและดูแล
ระบบ Medical Equipment Pool บนเครื่อง Windows ภายในโรงพยาบาล

คำสั่งทั้งหมดเขียนไว้ตรงตามที่ต้องพิมพ์จริง ห้ามดัดแปลง

---

## 0. ขอบเขตและการจำแนกหลักฐาน (Scope & evidence classification)

**นี่ไม่ใช่ environment ที่สี่**

ระบบมี environment อย่างเป็นทางการเพียง 3 ชั้นเท่านั้น (OD-PR24-4):

| Environment | คำอธิบาย |
|---|---|
| Development | สำหรับพัฒนา |
| **Staging/UAT** | **สิ่งที่คู่มือนี้ครอบคลุม** |
| Production | ใช้งานจริง |

การรันบนเครื่อง Windows ในโรงพยาบาลคือ **วิธีการรัน (execution method)
ของ Staging/UAT** ไม่ใช่ environment ใหม่ และไม่ใช่ Production

**การจำแนกหลักฐาน (สำคัญมาก):**

- ผลการซ้อม restore ในคู่มือนี้จัดเป็น **LOCAL REHEARSAL** เท่านั้น
- **ไม่นับ** เป็น managed-Staging restore rehearsal
- **ไม่นับ** เป็นหลักฐาน Production GO
- แม้ผลจะ PASS ทุกข้อ ก็ยังต้องซ้อมบน managed Staging อีกครั้งก่อนขึ้น Production

## 1. สิ่งที่ต้องมีก่อนติดตั้ง (Prerequisites)

1. **Windows** พร้อมสิทธิ์ Administrator บนเครื่องนั้น
2. **Docker Desktop** ติดตั้งแล้วและ **เปิดทำงานอยู่**
   - ระบบติดตั้ง **ไม่** ติดตั้ง Docker ให้อัตโนมัติ
   - ถ้า Docker ไม่ทำงาน ทุกคำสั่งในคู่มือนี้จะหยุดทันทีพร้อมข้อความแจ้ง
3. **PowerShell**
4. พื้นที่ว่างในดิสก์อย่างน้อย ~5 GB
5. ไฟล์โปรเจกต์ (repository) อยู่บนเครื่องแล้ว

เปิด PowerShell แล้วเข้าไปที่โฟลเดอร์:

```powershell
cd <path-to-repo>\deployment\local-staging
```

## 2. ติดตั้งครั้งแรก (First install)

```powershell
.\install.ps1
```

ลำดับที่ระบบจะทำให้ (อัตโนมัติ):

1. ตรวจสอบ prerequisites
2. ตรวจสถานะปัจจุบัน (ไม่ต้องมีไฟล์ตั้งค่าก่อน)
3. **สร้างไฟล์ตั้งค่าและรหัสลับใหม่** (เฉพาะการติดตั้งครั้งแรก)
4. build อิมเมจของ backend/frontend จากซอร์สปัจจุบัน
5. เปิด PostgreSQL และรอจนพร้อม
6. เปิด Redis (ถ้าไม่ขึ้น ไม่ถือเป็นข้อผิดพลาด — ดูข้อ 2.2)
7. รัน database migration
8. เปิดแอปพลิเคชันและรอจนพร้อมใช้งาน
9. **สร้างผู้ดูแลระบบ (Administrator) — บังคับ**
10. บันทึกสถานะว่าติดตั้งสำเร็จ และแสดง URL สำหรับใช้งานผ่าน LAN

### 2.1 ข้อมูลจะถูกเก็บไว้ที่ไหน

- ข้อมูล PostgreSQL อยู่ใน **Docker volume** — คงอยู่แม้จะ stop/start
- ไฟล์ตั้งค่า `.env` อยู่ในโฟลเดอร์ `deployment\local-staging\`
- **ห้ามลบหรือแก้ไข `.env` ด้วยตนเอง** — รหัสลับทั้งหมดอยู่ในนั้น

### 2.2 Redis ล่มไม่เป็นไร (non-blocking)

ตามสถาปัตยกรรมของระบบ Redis เป็น **non-blocking**

- PostgreSQL: **จำเป็น** — ถ้าไม่ขึ้น ระบบไม่พร้อมใช้งาน
- Redis: **ไม่บังคับ** — ถ้าไม่ขึ้น ระบบยังทำงานได้ (แค่ประสิทธิภาพ cache ลดลง)

`status.ps1` จะแสดงว่า `Redis: Degraded` ซึ่ง **ไม่ใช่** เหตุให้หยุดใช้งาน

### 2.3 รหัสผ่านผู้ดูแลระบบชั่วคราว (สำคัญ)

ระหว่างติดตั้ง ระบบจะถามข้อมูลผู้ดูแลระบบ (รหัสพนักงาน, อีเมล, ชื่อ-นามสกุล)

จากนั้นระบบจะ **สร้างรหัสผ่านชั่วคราวให้เอง และแสดงบนหน้าจอเพียงครั้งเดียว**

- **บันทึกรหัสผ่านนั้นทันที** ก่อนปิดหน้าต่าง
- รหัสผ่านนี้ **ไม่ถูกบันทึกลงไฟล์ log ใด ๆ**
- **เข้าสู่ระบบแล้วเปลี่ยนรหัสผ่านทันที** ผ่านเมนูของแอปพลิเคชัน
- ถ้าทำรหัสผ่านหาย ให้ติดต่อผู้ดูแลระบบระดับสูงกว่า อย่าพยายามแก้ไขฐานข้อมูลเอง

### 2.4 ถ้าติดตั้งล้มเหลวกลางคัน

ถ้าการสร้าง Administrator ล้มเหลว ระบบจะ **ไม่** บันทึกว่าติดตั้งสำเร็จ

วิธีแก้: **รัน `.\install.ps1` ใหม่อีกครั้ง** (ไม่ใช่ `update.ps1`)

การรัน install ซ้ำจะ:
- เก็บ `.env` และรหัสลับเดิมไว้
- เก็บข้อมูลใน PostgreSQL ไว้
- พยายามสร้าง Administrator อีกครั้ง
- บันทึกว่าสำเร็จก็ต่อเมื่อมี Administrator แล้วจริง

### 2.5 Firewall และการเข้าใช้งานผ่าน LAN

- ระบบ **ไม่แก้ไข firewall ให้อัตโนมัติ** โดยเจตนา
- ถ้าเครื่องอื่นใน LAN เข้าไม่ได้ ผู้ดูแลเครือข่ายอาจต้องเปิด port ให้เอง
- PostgreSQL และ Redis **ไม่ถูกเปิดออกสู่ LAN** และต้องไม่เปิด

## 3. การใช้งานประจำวัน (Daily operation)

| คำสั่ง | ทำอะไร |
|---|---|
| `.\start.ps1` | เปิดระบบที่ติดตั้งไว้แล้ว |
| `.\stop.ps1` | หยุดระบบ |
| `.\status.ps1` | ดูสถานะ |

**สิ่งที่ต้องเข้าใจ:**

- `stop.ps1` **ไม่ลบข้อมูล** — ฐานข้อมูล ไฟล์ตั้งค่า และ backup ยังอยู่ครบ
- `start.ps1` **ไม่** สร้างรหัสลับใหม่ และ **ไม่** รัน migration
- **Docker Desktop ต้องเปิดอยู่เสมอ** ก่อนใช้คำสั่งเหล่านี้
- `status.ps1` จะแสดง `Redis: Degraded (...)` ถ้า Redis มีปัญหา ซึ่งไม่บล็อกการใช้งาน

## 4. สำรองข้อมูล (Backup)

```powershell
.\backup.ps1
```

### 4.1 เก็บไว้ที่ไหน

```
deployment\local-staging\backups\
```

แต่ละครั้งจะได้ 2 ไฟล์:

- `mep-postgres-local-staging-<เวลา UTC>.dump` — ตัวข้อมูล
- `...dump.manifest.json` — ข้อมูลกำกับ (checksum, Alembic revision ฯลฯ)

**backup อยู่นอก Docker volume** จึงยังอยู่แม้จะ stop/start หรือ uninstall แบบปกติ
และคัดลอกไปเก็บที่อื่นได้ด้วยการ copy ไฟล์ธรรมดา

**แนะนำอย่างยิ่ง:** คัดลอก backup ไปเก็บไว้อีกที่หนึ่ง (เช่น external drive
หรือ network share) — backup ที่อยู่บนเครื่องเดียวกับระบบ ไม่ช่วยอะไร
ถ้าเครื่องนั้นเสียทั้งเครื่อง

### 4.2 หา backup ล่าสุดได้อย่างไร

เรียงตามชื่อไฟล์ — เวลาใน UTC ต่อท้ายชื่อ ไฟล์ที่ชื่อมากที่สุดคือใหม่ที่สุด

### 4.3 การเก็บย้อนหลัง (retention)

- เก็บไว้ **30 วัน** (นโยบายที่ Owner อนุมัติ)
- `backup.ps1` จะลบไฟล์ที่เก่ากว่านั้นให้เอง
- **ไฟล์ล่าสุดจะไม่ถูกลบ** แม้จะเก่ากว่า 30 วัน
- ลบเฉพาะไฟล์ backup ในโฟลเดอร์นั้น ไม่แตะไฟล์อื่น

### 4.4 `Checksum verification: PASS` แปลว่าอะไร

**แปลว่า:** ไฟล์ backup ที่ได้ ตรงกับ checksum ที่บันทึกไว้ — ไม่เสียหายระหว่างเขียน

**ไม่ได้แปลว่า:** ไฟล์นี้ restore กลับมาได้จริง

การจะรู้ว่า restore ได้จริง ต้อง**ซ้อม restore** ตามข้อ 5

> **ห้ามแก้ไขไฟล์ manifest หรือ checksum ด้วยตนเอง** ไม่ว่ากรณีใด
> ถ้า checksum ไม่ตรง แปลว่า backup นั้นมีปัญหาจริง

## 5. ซ้อมกู้คืนข้อมูล (Restore rehearsal)

```powershell
.\restore.ps1
```

### 5.1 ปลอดภัยโดยค่าเริ่มต้น

คำสั่งนี้ **ไม่เขียนทับฐานข้อมูลที่ใช้งานอยู่** และไม่มีตัวเลือกให้ทำเช่นนั้น

สิ่งที่เกิดขึ้น:

1. สร้างฐานข้อมูลชั่วคราวชื่อ `mep_local_restore_rehearsal_<เวลา>`
2. ตรวจ checksum
3. restore ลงฐานข้อมูลชั่วคราวนั้น
4. ตรวจ Alembic revision ว่าตรงกับที่บันทึกไว้
5. ตรวจจำนวนแถวของตารางตัวแทน
6. รายงาน PASS/FAIL พร้อมเวลาที่ใช้
7. **ลบฐานข้อมูลชั่วคราวทิ้ง**

ฐานข้อมูลที่ใช้งานจริง **ไม่ถูกแตะต้องเลย**

ถ้าต้องการเก็บฐานข้อมูลชั่วคราวไว้ตรวจสอบ:

```powershell
.\restore.ps1 -KeepRehearsalDatabase
```

### 5.1.1 เลือกไฟล์ backup เอง

โดยค่าเริ่มต้นระบบจะซ้อมกู้คืนจาก backup ล่าสุด ถ้าต้องการระบุไฟล์เอง:

```powershell
.\restore.ps1 -Backup "D:\external-drive\mep-postgres-local-staging-20260904T010000Z.dump"
```

ข้อกำหนด:

- ไฟล์ `.manifest.json` ต้องอยู่ข้างไฟล์ `.dump` นั้นด้วย มิฉะนั้นระบบจะ
  **ปฏิเสธทันที** เพราะ checksum และ source identity ถูกอ่านจาก manifest
- ไฟล์ที่อยู่นอกโฟลเดอร์ `backups` จะถูกคัดลอกพร้อม manifest เข้าไปยัง
  โฟลเดอร์ชั่วคราวก่อนซ้อม แล้วลบทิ้งเมื่อเสร็จ — ระบบจะซ้อมกู้คืน
  **ไฟล์ที่ระบุเท่านั้น** ไม่ใช่ไฟล์ชื่อเดียวกันที่บังเอิญอยู่ในโฟลเดอร์ `backups`

### 5.2 คำเตือน

> **ห้าม restore ทับฐานข้อมูลที่ใช้งานอยู่** เว้นแต่จะมีขั้นตอนกู้คืนจริง
> ที่ Owner อนุมัติแล้ว ซึ่ง **ยังไม่มีใน PR24D-L3**
>
> หากต้องกู้คืนข้อมูลจริง ให้ติดต่อผู้ดูแลระบบระดับสูงกว่าก่อนเสมอ
> อย่าดำเนินการเอง

### 5.3 การจำแนกหลักฐาน

ผล PASS จาก `.\restore.ps1` = **LOCAL REHEARSAL**

**ไม่เท่ากับ** managed-Staging rehearsal และ**ไม่ใช่**หลักฐานสำหรับ Production GO

## 6. อัปเดตระบบ (Update)

```powershell
.\update.ps1
```

### 6.1 ลำดับการทำงาน

1. ตรวจว่าเคยติดตั้งสำเร็จมาก่อน
2. build อิมเมจใหม่จากซอร์สปัจจุบัน
3. **สำรองข้อมูล (บังคับ)** ← ถ้าขั้นนี้ล้มเหลว จะหยุดทันที
4. หยุดแอปพลิเคชัน (ถ้ากำลังทำงานอยู่)
5. ตรวจว่า PostgreSQL พร้อม
6. รัน migration
7. เปิดแอปพลิเคชันและรอจนพร้อม
8. บันทึกสถานะ

### 6.2 กฎสำคัญ

- **ไม่มี backup = ไม่อัปเดต** ไม่มีตัวเลือกให้ข้ามขั้นตอนนี้
- ถ้า **backup ล้มเหลว** → ระบบที่กำลังทำงานอยู่ **ไม่ถูกหยุด** และ **ไม่มี migration**
- ถ้า **migration ล้มเหลว** → สถานะจะไม่ถูกบันทึกว่าอัปเดตสำเร็จ
- หลังอัปเดตสำเร็จ ระบบจะ **เปิดทำงานอยู่เสมอ** แม้ก่อนหน้านั้นจะหยุดอยู่

## 7. ถอนการติดตั้ง (Uninstall)

### 7.1 แบบปกติ (ปลอดภัย)

```powershell
.\uninstall.ps1
```

- ลบเฉพาะ container
- **ข้อมูล PostgreSQL ยังอยู่**
- **`.env` ยังอยู่**
- **โฟลเดอร์ `backups\` ยังอยู่ครบ**

ติดตั้งใหม่ด้วย `.\install.ps1` จะกลับมาใช้ข้อมูลและรหัสลับเดิม

### 7.2 แบบลบข้อมูล (อันตราย)

```powershell
.\uninstall.ps1 -RemoveData
```

- ต้องพิมพ์ข้อความยืนยันให้ตรงเป๊ะ มิฉะนั้นจะยกเลิก
- ลบ volume ของ PostgreSQL/Redis และไฟล์ `.env`
- **โฟลเดอร์ `backups\` จะไม่ถูกลบ** — ไฟล์ backup ยังอยู่

> ถ้าต้องการลบไฟล์ backup ด้วย ต้องลบโฟลเดอร์ `backups\` ด้วยตนเอง
> ระบบจะไม่ลบให้โดยอัตโนมัติ เพราะถือว่าเป็นข้อมูลสำคัญ

## 8. แก้ปัญหาเบื้องต้น (Troubleshooting)

| อาการ | แปลว่า | ทำอย่างไร |
|---|---|---|
| `Docker Engine is not available` | Docker Desktop ไม่ได้เปิด | เปิด Docker Desktop รอจนพร้อม แล้วรันคำสั่งใหม่ |
| `Port ... is already in use` | มีโปรแกรมอื่นใช้ port อยู่ | ปิดโปรแกรมนั้น หรือแจ้งผู้ดูแลเครือข่ายเพื่อเปลี่ยน port |
| `PostgreSQL did not become healthy in time` | ฐานข้อมูลไม่พร้อม | รัน `.\status.ps1`; ถ้ายังไม่หาย แจ้งผู้ดูแลระบบ **อย่าลบ volume เอง** |
| `Redis: Degraded` | Redis ไม่ทำงาน | **ไม่ต้องทำอะไร** ระบบยังใช้งานได้ แจ้งผู้ดูแลระบบเมื่อสะดวก |
| `The application did not become ready in time` | backend ยังไม่พร้อม | รัน `.\status.ps1`; ลอง `.\stop.ps1` แล้ว `.\start.ps1`; ถ้ายังไม่หาย แจ้งผู้ดูแลระบบ |
| `Database migration failed` | migration ไม่สำเร็จ | **ข้อมูลยังปลอดภัย** และแอปไม่ถูกเปิด แจ้งผู้ดูแลระบบทันที อย่ารันซ้ำเรื่อย ๆ |
| `Database backup FAILED` | สำรองข้อมูลไม่สำเร็จ | ตรวจพื้นที่ดิสก์ว่าง; ถ้าเกิดตอน update ระบบเดิมยังทำงานปกติ แจ้งผู้ดูแลระบบ |
| `Backup checksum verification FAILED` | ไฟล์ backup เสียหาย | **อย่าใช้ backup นั้น** สั่ง `.\backup.ps1` ใหม่ และแจ้งผู้ดูแลระบบ |
| `Restore rehearsal FAILED` | backup กู้คืนไม่ได้ | ถือว่า backup นั้นใช้ไม่ได้ แจ้งผู้ดูแลระบบทันที เพราะแปลว่าการสำรองข้อมูลมีปัญหาจริง |
| `Administrator bootstrap failed` | สร้างผู้ดูแลระบบไม่สำเร็จ | รัน `.\install.ps1` ใหม่ (ดูข้อ 2.4) |
| `Another ... operation is already in progress` | มีคำสั่งอื่นทำงานอยู่ | รอให้เสร็จก่อน แล้วลองใหม่ |
| เครื่องอื่นใน LAN เข้าไม่ได้ | firewall หรือเครือข่าย | ตรวจว่า `.\status.ps1` ขึ้น Ready บนเครื่องนี้ก่อน แล้วแจ้งผู้ดูแลเครือข่าย |

**หลักการสำหรับ operator:** ถ้าคำสั่งใดหยุดพร้อมข้อความ ERROR ให้อ่านบรรทัด
`ACTION:` ที่ระบบพิมพ์ไว้ และ **อย่าแก้ไขฐานข้อมูลหรือ Docker volume ด้วยตนเอง**

---

## 9. ข้อจำกัดที่ทราบ (Known limitations)

1. **ยังไม่มีขั้นตอนกู้คืนข้อมูลจริง (live recovery)** — `restore.ps1` ทำได้เฉพาะการซ้อม
2. **ยังไม่มีการสำรองข้อมูลอัตโนมัติตามเวลา** — `backup.ps1` ต้องสั่งเอง
   ดังนั้น **ยังไม่รับประกัน RPO ≤ 1 ชั่วโมง** การมี backup แบบสั่งเองไม่เท่ากับ
   การสำรองข้อมูลรายชั่วโมง
3. **backup อยู่บนเครื่องเดียวกับระบบ** — ต้องคัดลอกออกไปเก็บที่อื่นเอง
4. **ยังไม่มีตัวติดตั้งแบบหน้าจอ (Setup.exe)** — ใช้ PowerShell เท่านั้น
5. Local rehearsal **ไม่แทน** managed-Staging rehearsal

### เป้าหมายที่ Owner อนุมัติไว้ (อ้างอิง)

| รายการ | เป้าหมาย | สถานะปัจจุบัน |
|---|---|---|
| RPO | ≤ 1 ชั่วโมง | **ยังไม่ได้** (ยังไม่มี backup อัตโนมัติ) |
| RTO | ≤ 4 ชั่วโมง | วัดเวลา restore ได้จาก `.\restore.ps1` |
| Retention | 30 วัน | **ทำแล้ว** |
| Restore rehearsal ก่อน Production GO | ต้องทำบน managed Staging | **ยังค้างอยู่** |

## 10. ขอบเขตกับการย้ายขึ้นคลาวด์ในอนาคต

คู่มือนี้ครอบคลุมเฉพาะการรัน Staging/UAT บนเครื่องในโรงพยาบาลเท่านั้น

**ยังไม่ได้ทำ และไม่อยู่ในขอบเขตของ PR24D-L3:**

- ผู้ให้บริการคลาวด์ (ยังไม่เลือก, ยังไม่จ่ายเงิน)
- managed Staging ถาวร
- การ deploy ขึ้น Production
- การซ้อม backup/restore บน managed Staging

การตัดสินใจเหล่านี้เป็นของ Owner และจะทำในขั้นตอนถัดไป

## ภาคผนวก — สรุปคำสั่งทั้งหมด

```powershell
.\install.ps1                      # ติดตั้งครั้งแรก / ซ่อมการติดตั้งที่ไม่สมบูรณ์
.\start.ps1                        # เปิดระบบ
.\stop.ps1                         # หยุดระบบ (ข้อมูลยังอยู่)
.\status.ps1                       # ดูสถานะ
.\backup.ps1                       # สำรองข้อมูล + ลบไฟล์เก่าเกิน 30 วัน
.\restore.ps1                      # ซ้อมกู้คืน (ไม่แตะฐานข้อมูลจริง)
.\restore.ps1 -KeepRehearsalDatabase   # ซ้อมกู้คืน แล้วเก็บฐานข้อมูลชั่วคราวไว้
.\update.ps1                       # อัปเดต (บังคับสำรองข้อมูลก่อน)
.\uninstall.ps1                    # ถอนการติดตั้ง (ข้อมูลและ backup ยังอยู่)
.\uninstall.ps1 -RemoveData        # ถอนการติดตั้งและลบข้อมูล (ต้องยืนยัน)
```

> **หมายเหตุเรื่องความปลอดภัย:** เอกสารนี้ไม่มีรหัสผ่าน, JWT secret,
> รหัสผ่าน PostgreSQL หรือ DATABASE_URL จริงอยู่เลย และต้องไม่มีตลอดไป
> หากต้องยกตัวอย่าง ให้ใช้ค่าสมมติเท่านั้น
