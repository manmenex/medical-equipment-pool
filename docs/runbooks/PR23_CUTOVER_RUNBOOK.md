# Cutover Runbook — Medical Equipment Pool (Roadmap PR23)
## คู่มือปฏิบัติการเปลี่ยนระบบ (Cutover) — ระบบบริหารจัดการเครื่องมือแพทย์ส่วนกลาง

**Status:** Operational execution document. Governs the one-time
transition from the legacy AppSheet operational system to this
repository's Medical Equipment Pool web application.
เอกสารนี้ใช้สำหรับปฏิบัติจริงเมื่อทำการเปลี่ยนระบบ (cutover) จากระบบ AppSheet
เดิม มาเป็นระบบ Medical Equipment Pool (เว็บแอปพลิเคชัน) — เป็นการเปลี่ยนระบบ
เพียงครั้งเดียว (one-time transition)
**Authority:** `docs/design/PR23_CUTOVER_READINESS_PLAN.md` controls the
underlying architecture, gates, and Owner Decisions (OD-PR23-1 through
OD-PR23-6) this runbook operationalizes. Where this runbook and that
design document conflict, the design document controls, and the
conflict must be reported, not silently resolved here.
**Authoritative baseline this runbook was written against:**
`8644536403eeec269e6dadf835f1bda3844b6cce` (GitHub PR #127, PR23E —
Cutover Readiness Frontend / Operator Workflow, merged).
**Maintainer:** Documentation/Governance Engineer.

## 0. อ่านก่อนเริ่มปฏิบัติ (Read this first)

**การที่ Roadmap PR23 (ความสามารถของแอปพลิเคชันในการบันทึกและแสดงความ
พร้อมก่อนเปลี่ยนระบบ) เสร็จสมบูรณ์ ไม่ได้แปลว่าเหตุการณ์ต่อไปนี้เกิดขึ้นจริงแล้ว:**

- Pilot (การทดลองใช้จริงกับหอผู้ป่วยที่กำหนด) ยังไม่ได้ดำเนินการ
- การเปลี่ยนระบบจริง (Production cutover) ยังไม่เกิดขึ้น
- AppSheet ยังไม่ได้ถูกทำให้เป็นโหมดอ่านอย่างเดียว (read-only) จริง
- ยังไม่ได้รับการอนุมัติ/ลงนาม (sign-off) จาก UAT/Pilot/Production
- ยังไม่ได้เลือกเป้าหมายของระบบ production ที่จะใช้งานจริง
- การสำรองข้อมูลและกู้คืนข้อมูล (backup/restore) ยังไม่ได้ทดสอบจริงว่าสำเร็จ

**เอกสารนี้กำหนดว่าต้องมีหลักฐานอะไรบ้างก่อนดำเนินการต่อ — เอกสารนี้ไม่สามารถ
สร้างหลักฐานเหล่านั้นขึ้นมาได้เอง** รายการตรวจสอบ (checklist) ข้อใดที่ยังไม่
สำเร็จจริง ถือเป็นเงื่อนไขห้ามดำเนินการต่อ (genuine blocker) ไม่ใช่เพียงหมายเหตุ
ให้ผ่านไปก่อน

**รูปแบบการเปลี่ยนระบบที่ได้รับอนุมัติ (OD-PR23-1): Hard cutover (เปลี่ยนระบบ
แบบเด็ดขาดครั้งเดียว)** หลังจากเปลี่ยนระบบแล้ว **AppSheet จะกลายเป็นระบบอ่าน
อย่างเดียว/เก็บถาวร (read-only/archive)** สำหรับผู้ใช้งานปฏิบัติการ ระบบ Medical
Equipment Pool ใหม่จะเป็น**ระบบเดียว**ที่สามารถบันทึกข้อมูลปฏิบัติการได้
**ห้ามมีการเขียนข้อมูลพร้อมกันทั้งสองระบบ (uncontrolled dual-write) โดยเด็ดขาด
ตลอดเวลา** — ทั้งสองระบบจะไม่สามารถรับการบันทึกรายการปฏิบัติการจริงพร้อมกัน
ได้เลย

## 1. บทบาทและความรับผิดชอบ (Roles and responsibilities)

คู่มือนี้**ไม่ได้เพิ่ม role ที่ 4** ในระบบแอปพลิเคชัน — ระบบสิทธิ์ยังคงมีเพียง 3
role เดิม (`administrator`, `equipment_pool_staff`, `read_only`) บทบาท
ด้านล่างนี้เป็น**บทบาทเชิงการกำกับดูแลปฏิบัติการ (operational governance
role)** ที่มอบหมายให้บุคคลจริงสำหรับการเปลี่ยนระบบครั้งนี้ — อาจเป็นคนเดียวกัน
หรือคนละคนกับผู้ถือ role ในแอปพลิเคชันก็ได้

| บทบาทเชิงปฏิบัติการ | ความรับผิดชอบ | Role ในแอปพลิเคชันที่มักถือ |
|---|---|---|
| **A. ผู้อนุมัติปฏิบัติการที่รับผิดชอบ (Accountable operational approver)** | มีอำนาจตัดสินใจ Go/No-Go ขั้นสุดท้าย (§7) และอนุมัติการ rollback (§9/§10) ตามธรรมาภิบาลที่อนุมัติแล้ว (OD-PR23-3) | ไม่ได้ถูกกำหนดตายตัวโดยสถาปัตยกรรม — อาจเป็นหรือไม่เป็นผู้ถือ role `administrator` ก็ได้ |
| **B. ผู้ดูแลระบบที่บันทึกการตัดสินใจ (Application Administrator)** | บันทึกหลักฐาน Gate G / การตัดสินใจ GO-NO_GO **ในแอปพลิเคชัน** ผ่านหน้าจอ PR23E / API ของ PR23D | `administrator` (บังคับใช้โดย backend) |
| **C. เจ้าหน้าที่ Equipment Pool** | ตรวจสอบสถานะปัจจุบันของเครื่องมือจริง (§8), ปฏิบัติงาน Issue/Receive ตามปกติ, ทำการออกเครื่องใหม่ด้วยมือ (manual re-issue) เมื่อจำเป็น (§11) | `equipment_pool_staff` |
| **D. ผู้รับผิดชอบด้านเทคนิค/deployment** | ยืนยันความพร้อมของ deployment/ฐานข้อมูล/backup/health ก่อนที่จะถือว่า Gate A ผ่าน (§15/§16) — ไม่ใช่ผู้อนุมัติ Go/No-Go โดยอัตโนมัติ | ไม่ใช่ role ในแอปพลิเคชัน — เป็นความรับผิดชอบเชิงโครงสร้างพื้นฐาน |
| **E. ผู้ประสานงานหอผู้ป่วยนำร่อง (Pilot Ward contact)** | จุดติดต่อของหอผู้ป่วยที่ทำ Pilot (§12) ระหว่างช่วง Pilot | ไม่ใช่ role ในแอปพลิเคชัน |

## 3. รายการโครงสร้างพื้นฐานที่ยังเปิดอยู่ — ห้ามระบุว่าปิดแล้ว

ตามหลักฐานอ้างอิงของรีโพซิทอรีนี้เอง
(`docs/audits/04-consolidated-implementation-plan.md` §14 ข้อ 7;
`docs/ARCHITECTURE_DECISIONS.md`, "Managed deployment preferred") ณ
baseline ที่เอกสารนี้อ้างอิง:

- **ยังไม่ได้เลือกแพลตฟอร์ม/ผู้ให้บริการสำหรับ production deployment**
  แนวทางที่ต้องการคือ managed deployment (production ต้องไม่สมมติว่ามีสิทธิ์
  เข้าถึง server ของโรงพยาบาลโดยตรง) แต่ยังไม่ได้เลือกแพลตฟอร์มที่ชัดเจน
  เอกสารนี้**ไม่ได้เลือก**แพลตฟอร์มให้
- **ยังไม่เคยมีการออกแบบหรือทดสอบกระบวนการ backup/restore จริงในรีโพซิทอรี
  นี้** ถูกระบุไว้ว่าเป็นเงื่อนไขที่ยังเปิดอยู่ (open) สำหรับ Pilot/Production
  Readiness ไม่ใช่สิ่งที่คู่มือนี้ — หรือ PR เอกสารใดๆ — จะปิดได้ด้วยการเขียน
  ข้อความเท่านั้น

**กฎ fail-closed:** หากรายการใดข้างต้นยังไม่มีหลักฐานจริงรองรับ ณ เวลาที่มีการ
ประเมิน Gate A สำหรับการเปลี่ยนระบบจริง **ต้องบล็อก GO ไว้เสมอ** การที่คู่มือนี้
ระบุว่า "ต้องมีหลักฐานอะไรบ้าง" ไม่เท่ากับ "มีหลักฐานนั้นแล้ว" ดู §15/§16 สำหรับ
ช่องหลักฐานที่คู่มือนี้กำหนดไว้แต่ไม่สามารถกรอกล่วงหน้าให้ได้

## 4. กฎช่วงหยุดระบบชั่วคราว (Freeze window rules)

```
T0 — หยุดการเขียนข้อมูลในระบบ AppSheet เดิม
T1 — ดึงข้อมูลสุดท้ายจากระบบเดิม (ถ้าจำเป็นต้องมีรอบ import สุดท้าย)
T2 — ตรวจสอบ import/reconciliation/current-state ครั้งสุดท้าย (Gates B–E)
T3 — บันทึกการตัดสินใจ Go (Gate G)
T4 — เปิดให้เจ้าหน้าที่ Equipment Pool บันทึกข้อมูลปฏิบัติการในแอปพลิเคชันได้
```

ระหว่าง **T0 ถึง T4 ห้ามมีการเขียนข้อมูลปฏิบัติการที่ไม่ได้ควบคุมในระบบใดระบบ
หนึ่งเลย** ทั้ง AppSheet และแอปพลิเคชันใหม่จะถูกหยุดรับรายการ dispatch/receipt
ใหม่ในช่วงนี้ (แอปพลิเคชันใหม่ยังไม่มีการบันทึก GO และ AppSheet กำลังถูกหยุด
ตั้งแต่ T0)

### กรณีฉุกเฉิน/ข้อยกเว้นระหว่างช่วงหยุดระบบ

**ห้ามคิดค้นวิธีแก้ปัญหาทางเทคนิคขึ้นมาเอง** (ห้ามเขียน script เฉพาะกิจ ห้ามแก้
ข้อมูลในฐานข้อมูลโดยตรง ห้ามเขียนข้อมูลใน AppSheet "แค่ครั้งนี้ครั้งเดียว") หากมี
เหตุการณ์ทางคลินิกจริงที่ต้องเกิดขึ้นระหว่างช่วงหยุดระบบและรอถึง T4 ไม่ได้จริงๆ:

- [ ] บันทึกเหตุการณ์นั้นอย่างชัดเจน (อะไร เมื่อไหร่ ใคร ทำไมรอไม่ได้)
- [ ] มีการบันทึกการตัดสินใจเชิงปฏิบัติการที่มีผู้รับผิดชอบชัดเจน ระบุว่าใครเป็นผู้
      อนุมัติข้อยกเว้นนี้
- [ ] เหตุการณ์นั้นต้อง reconcile (กระทบยอด) ให้เรียบร้อยก่อนบันทึกการตัดสินใจ
      Go (T3) — ต้องสะท้อนอยู่ในหลักฐาน Gate D/E ไม่ใช่ปล่อยเป็นช่องว่างที่ไม่มี
      การบันทึก

**หากรีโพซิทอรี/โรงพยาบาลนี้มีกระบวนการฉุกเฉิน/downtime ที่อนุมัติแล้ว ให้อ้างอิง
ที่นี่:** `______________________` หากยังไม่มี นี่คือกระบวนการเชิงปฏิบัติการที่
**ต้อง**กำหนดให้ชัดเจนก่อนเปลี่ยนระบบจริง — ห้ามพยายามเปลี่ยนระบบโดยไม่มี
กระบวนการนี้

### T3 — การตัดสินใจ Go/No-Go

**ผู้ดูแลระบบ (Application Administrator, §1 บทบาท B)** เป็นผู้บันทึกการ
ตัดสินใจผ่านหน้าจอ PR23E ที่พัฒนาไว้แล้ว (`/cutover-readiness/:runId`) / API
ของ PR23D (`POST /cutover-readiness-runs/{run_id}/decision`)

**Backend คือแหล่งข้อมูลจริงเพียงแหล่งเดียวที่ตัดสินว่า GO ทำได้หรือไม่** กฎการ
แสดงผลของหน้าจอและ GO checklist (§7) เป็นเพียงแนวทางช่วยผู้ปฏิบัติงานเท่านั้น —
ไม่สามารถแทนที่หรือ override การประเมิน Gates A–F ใหม่แบบสดที่ backend ทำ ณ
ขณะส่งข้อมูลได้

- **GO** — ทำได้ก็ต่อเมื่อ backend ยอมรับการส่งข้อมูลเท่านั้น หาก backend
  ปฏิเสธ (เช่น `CUTOVER_DECISION_BLOCKED_BY_READINESS`,
  `CUTOVER_DECISION_WARNINGS_NOT_ACKNOWLEDGED` หรือ error code อื่นใด)
  แสดงว่า**ยังไม่ได้บันทึก**การตัดสินใจ — ให้ถือเหมือนความพยายาม GO ที่ล้มเหลว
  ไม่จำเป็นต้องทำตาม §8 (ขั้นตอน NO-GO) เว้นแต่ผู้อนุมัติที่รับผิดชอบตัดสินใจแยก
  ต่างหากที่จะบันทึก `NO_GO` อย่างชัดเจน
- **NO_GO** — หยุดการเปลี่ยนระบบและทำตาม §8 (ขั้นตอน NO-GO) `NO_GO` ยังคง
  ใช้งานได้แม้มี BLOCKER อยู่ — เพราะโดยการออกแบบ `NO_GO` คือการบันทึกว่า
  "ไม่อนุมัติ" ไม่ใช่การผ่าน readiness gate

**ห้าม override การปฏิเสธของ backend ด้วยมือโดยเด็ดขาด** (ห้ามเขียนข้อมูลลง
ฐานข้อมูลโดยตรง ห้ามข้าม API) หากผู้ปฏิบัติงานเห็นว่าการปฏิเสธนั้นไม่ถูกต้อง แสดง
ว่าเป็นข้อบกพร่องจริง — ให้หยุดและรายงาน ไม่ใช่หาทางเลี่ยง

### T4 — เปิดใช้งานปฏิบัติการจริง

หลังจากมีการบันทึกการตัดสินใจ `GO` ที่ถูกต้องและถาวรแล้วเท่านั้น (ยืนยันผ่าน
`GET .../decision` ที่คืนค่าการตัดสินใจที่บันทึกไว้จริง ไม่ใช่แค่ "หน้าจอแจ้งว่า
สำเร็จ"):

- [ ] แจ้งเจ้าหน้าที่ Equipment Pool ทุกคนว่าแอปพลิเคชันใหม่เป็นระบบเดียวที่ใช้
      บันทึกข้อมูลปฏิบัติการแล้ว
- [ ] ยืนยันว่า AppSheet ยังคงเป็น read-only/archive
- [ ] เจ้าหน้าที่เริ่มใช้ workflow ปกติสำหรับ Issue (`/borrow`) และ Receive
      (`/return`) สำหรับกิจกรรมปฏิบัติการจริงทั้งหมด
- [ ] บันทึกเวลา T4 จริง: `__________________`

**การบันทึกการตัดสินใจ `GO` เองไม่ได้เปลี่ยนสถานะของระบบใดๆ โดยอัตโนมัติ**
เป็นเพียงการบันทึกหลักฐาน เจ้าหน้าที่ปฏิบัติการต้องดำเนินขั้นตอน T4 ข้างต้นจริง —
ประกาศการเปลี่ยนแปลง ยืนยันว่า AppSheet ถูกล็อกแล้ว และเริ่มใช้แอปพลิเคชันตาม
ปกติ — การเปลี่ยนระบบจึงจะมีผลจริง

## 6. ขั้นตอนตรวจสอบ Gates A–F

ตรวจสอบแต่ละ gate ผ่านหน้าจอ gate-evaluation ของแอปพลิเคชันเองเท่านั้น —
**ห้าม**คำนวณผล gate เองในคู่มือนี้หรือด้วยการตรวจสอบข้อมูลดิบ คำตอบจาก
`GET .../gate-evaluation` คือแหล่งข้อมูลที่เชื่อถือได้

| Gate | ความหมาย |
|---|---|
| **Gate A** | ความพร้อมของแอปพลิเคชัน — PR ที่จำเป็นถูก merge แล้ว, CI ผ่านบน head ที่ deploy จริง, migration ถูก apply แล้ว, ตั้งค่า production ถูกต้อง, backup/restore ผ่านการทดสอบแล้ว (§3/§15) |
| **Gate B** | ความพร้อมของ Equipment Master — การ import จาก PR20 เสร็จสมบูรณ์กับข้อมูล inventory จริง, BCM/Item Number ถูกต้อง, การ mapping Ward ได้รับอนุมัติ |
| **Gate C** | ความพร้อมของประวัติข้อมูลเดิม — การ import ประวัติจาก PR21 เสร็จสมบูรณ์, มีการบันทึก checksum/แหล่งข้อมูลต้นทาง |
| **Gate D** | ความพร้อมของ reconciliation — ทุก finding มี disposition แล้ว, `requires_correction` เป็นศูนย์, มี sign-off สุดท้ายที่ถูกต้องตรงกับ run ที่ใช้ตัดสินใจ |
| **Gate E** | ความพร้อมของสถานะปัจจุบัน/สถานะจริง — สถานะเครื่องมือปัจจุบันถูกตรวจสอบแล้ว, เครื่องมือที่ค้างอยู่ถูกจัดการครบถ้วน (§8/§11), ไม่มีความขัดแย้งของ identity ที่ยังไม่แก้ |
| **Gate F** | ความพร้อมด้านปฏิบัติการ — ผู้ใช้งาน/role ตรงกับรายชื่อจริง, เจ้าหน้าที่ได้รับการฝึกอบรมแล้ว, workflow QR ตรวจสอบแล้ว, ทดสอบ issue/receive แบบ smoke test ผ่านแล้ว, กำหนดผู้รับผิดชอบ rollback/ติดต่อชัดเจนแล้ว |

แต่ละรายการที่แอปพลิเคชันคืนค่ามาจะมี category ดังนี้:

- **BLOCKER** — mandatory gate ยังไม่ผ่าน `GO` เป็นไปไม่ได้ในเชิงโครงสร้าง
  ตราบใดที่ยังมี BLOCKER อยู่ (backend บังคับใช้กฎนี้เองโดยอิสระจากหน้าจอ)
- **WARNING** — รายการที่ไม่บังคับ (non-mandatory) ยังไม่เสร็จสมบูรณ์ `GO`
  ยังทำได้ แต่ผู้ปฏิบัติงานต้อง acknowledge (ยืนยันรับทราบ) ทุกรายการ WARNING
  ที่ยังมีผลอยู่ ตามสัญญาของ backend (ดู GO checklist ใน §7)
- **INFO** — ข้อมูลประกอบเท่านั้น ไม่มีผลต่อการบล็อก

**WARNING ประเภท manual attestation หมายความว่าซอฟต์แวร์ไม่สามารถพิสูจน์
ได้ว่าการกระทำในโลกจริงเกิดขึ้นแล้ว** การ acknowledge เป็นการบันทึกว่ามีมนุษย์
ตรวจสอบและยืนยันสภาพจริงแล้ว — ไม่ใช่สิ่งเดียวกันกับการตรวจสอบอัตโนมัติ และ
ไม่สามารถใช้แทนกันได้ ห้าม acknowledge รายการ manual attestation โดยไม่ได้
ตรวจสอบสภาพจริงนั้นจริงๆ

## 7. ขั้นตอน Gate G / Go-No-Go

**Gate G คือการตัดสินใจ Go/No-Go ที่บันทึกถาวรและแก้ไขไม่ได้ (immutable)**
มีเพียง role `administrator` เท่านั้นที่สามารถบันทึกได้ในแอปพลิเคชัน (บังคับใช้
โดย backend, `ADMINISTRATOR_ONLY_ROLES`) ผู้มีอำนาจปฏิบัติการที่รับผิดชอบ
(§1 บทบาท A) อาจเป็นคนละคนกับผู้ดูแลระบบที่ปฏิบัติงานประจำวัน (§1 บทบาท B) —
ตารางผู้รับผิดชอบในคู่มือนี้บันทึกทั้งสองบทบาทไว้

**การบันทึก `GO` ไม่ได้ทำสิ่งต่อไปนี้โดยอัตโนมัติ:**

- ปิด AppSheet
- เปิดใช้งาน production environment
- ย้ายข้อมูล (migrate)
- แก้ไขข้อมูล `Equipment` ใดๆ
- เริ่ม Pilot
- ทำ rollback

เป็นเพียงการบันทึกหลักฐานการอนุมัติเท่านั้น **การบันทึก `NO_GO` ไม่จำเป็นต้องผ่าน
readiness ก่อน** — เป็นกลไกสำหรับบันทึกว่า "ไม่อนุมัติ" ไม่ว่าสถานะ gate จะเป็น
อย่างไร

### GO checklist (ก่อนส่งข้อมูล GO ทันที)

- [ ] เลือก readiness run ที่ถูกต้อง (ตรงกับ run ID ที่บันทึกไว้ใน §2)
- [ ] `status` ของ run เป็น `completed`
- [ ] run เป็นข้อมูลล่าสุด — ไม่ถูกแทนที่ (superseded) โดย run ใหม่กว่า
      (ตรวจสอบ `supersedes_run_id`)
- [ ] `expected_version` ที่ส่งตรงกับ `version` ปัจจุบันของ run
- [ ] Gates A–F ถูก refresh แล้ว (ดึงข้อมูลใหม่ ไม่ใช่จากภาพหน้าจอเก่าหรือความจำ)
- [ ] ไม่มี BLOCKER ที่ยังมีผลอยู่
- [ ] ทุก WARNING ที่ยังมีผลอยู่ถูกตรวจสอบจริงและจะถูก acknowledge ในการส่ง
      ข้อมูล
- [ ] ระบุผู้อนุมัติที่รับผิดชอบแล้ว (§1 บทบาท A) และได้อนุมัติ GO ครั้งนี้แล้ว
- [ ] ผู้อนุมัติเชิงปฏิบัติการตรงกับที่บันทึกไว้ใน §1/§2
- [ ] หลักฐาน T0/T1/T2 ครบถ้วนแล้ว (§5)
- [ ] ช่วงหยุดระบบยังคงถูกควบคุมอยู่ (ไม่มีการเขียนข้อมูลที่ไม่ได้ควบคุมในระบบใด
      ตั้งแต่ T0)
- [ ] ตรวจสอบความพร้อม/การเข้าถึง production แล้ว (`GET /api/v1/health`
      ตอบกลับปกติ; §16)
- [ ] ผู้มีอำนาจ rollback (§1 บทบาท A หรือผู้สำรอง) พร้อมและติดต่อได้ในขณะนี้

**Checklist นี้ไม่สามารถแทนที่การบังคับใช้กฎของ backend ได้** backend จะ
ประเมิน Gates A–F ใหม่โดยอิสระ ณ ขณะที่ส่งข้อมูล และจะปฏิเสธคำขอไม่ว่า
checklist นี้จะระบุว่าอย่างไร หากหลักฐานจริง ณ ขณะนั้นไม่รองรับ GO

### ขั้นตอน NO-GO

หากบันทึก `NO_GO` (หรือ `GO` ถูกปฏิเสธและผู้มีอำนาจที่รับผิดชอบเลือกที่จะไม่ลอง
ใหม่ทันที):

- [ ] ห้ามดำเนินการต่อไปยัง T4
- [ ] บันทึกเหตุผล (structured error code หรือเหตุผลที่ผู้อนุมัติระบุเองสำหรับ
      `NO_GO`)
- [ ] ระบุ gate/หลักฐานที่ยังไม่ผ่านให้ชัดเจน
- [ ] คงไว้ หรือคืนสถานะเส้นทางปฏิบัติการเดิม (AppSheet) ตามขอบเขตที่อนุมัติแล้ว
      (§9) — หากยังไม่ได้ทำ T0 แสดงว่า AppSheet ไม่เคยถูกหยุด จึงไม่ต้องคืนสถานะ
      ใดๆ; หากทำ T0 ไปแล้ว ให้ทำตาม §9 (rollback ก่อนมีรายการ production แรก)
- [ ] แก้ไขปัญหาต้นเหตุผ่านระบบ/กระบวนการเจ้าของข้อมูลนั้น — ห้ามแก้ไขแบบ
      เฉพาะกิจภายในคู่มือนี้หรือในโมเดลหลักฐานของแอปพลิเคชัน
- [ ] หากต้องเก็บหลักฐานใหม่ ให้สร้าง `CutoverReadinessRun` **ใหม่** ที่แทนที่ตัว
      เดิม (`supersedes_run_id`) — ห้ามแก้ไข run เดิม

**ห้ามแก้ไขหลักฐาน readiness/decision เดิมที่ถาวรแล้ว ห้ามลบบันทึกการ
ตัดสินใจเดิม** เมื่อบันทึก `NO_GO` แล้ว ถือเป็นประวัติถาวร — แนวทางต่อไปคือสร้าง
run/decision ใหม่เสมอ ไม่ใช่แก้ไขของเดิม

---

## 8. ขั้นตอนการออกเครื่องใหม่ด้วยมือ / สถานะปัจจุบัน (Manual re-issue)

รักษา OD-PR23-2 ไว้ทุกประการ สถานะปัจจุบันของเครื่องมือทางกายภาพ**ต้องตรวจ
สอบด้วยมือจริง (manual/physical verification)** เสมอ — ไม่มีการอนุมานจาก
ประวัติข้อมูลเดิมโดยอัตโนมัติ ข้อมูล `LegacyEquipmentEvent` เป็นเพียงหลักฐาน
เท่านั้น

สำหรับเครื่องมือที่ตรวจสอบแล้วว่า**ถูกยืมออกอยู่จริง**แต่**ไม่มี** `BorrowTransaction`
สถานะ OPEN ในแอปพลิเคชันรองรับไว้:

- [ ] เจ้าหน้าที่ระบุเครื่องมือโดยใช้ BCM Code หรือ QR code ของ Item Number
      เดิมที่มีอยู่แล้ว (ไม่มีการสร้าง identifier ใหม่ ไม่มีการพิมพ์ QR ใหม่ — §13)
- [ ] เจ้าหน้าที่ระบุ/เลือก Ward ที่**มีอยู่แล้วจริง**จาก master data ของ
      แอปพลิเคชัน
- [ ] เจ้าหน้าที่ใช้ **workflow Issue ปกติที่มีอยู่แล้ว** (`/borrow`) — เหมือนกับ
      การ Issue ทั่วไปทุกประการ
- [ ] กฎของ backend ปกติยังคงมีผลบังคับใช้เต็มรูปแบบ (การป้องกันรายการ OPEN
      ซ้ำ, การควบคุม concurrency — ไม่มีการเปลี่ยนแปลง)

**ห้าม:**

- Issue เครื่องมือเป็นชุดจำนวนมาก (bulk issue)
- ย้อนวันที่รายการ (backdate)
- เล่นซ้ำ (replay) เหตุการณ์ `ISSUE` จากระบบเดิมโดยอัตโนมัติ
- สร้างหรือใช้ workflow issue แยกต่างหากสำหรับการเปลี่ยนระบบ
- สร้าง Ward ใหม่จากข้อความดิบของระบบเดิม

## 9. Rollback — ก่อนมีรายการ production รายการแรก

**ขอบเขต (OD-PR23-4): ก่อนที่จะมีรายการปฏิบัติการจริงรายการแรกถูกยอมรับใน
แอปพลิเคชันใหม่ อนุญาตให้ทำ rollback แบบเต็มรูปแบบได้ตามขั้นตอนที่อนุมัติแล้ว
นี้**

- [ ] หยุดการใช้งานปฏิบัติการในระบบใหม่ (เจ้าหน้าที่หยุดบันทึกรายการใหม่ใน
      แอปพลิเคชัน)
- [ ] ยืนยัน — อย่าสันนิษฐานเอง — ว่าไม่มีรายการ production จริงถูกบันทึกใน
      แอปพลิเคชันเลย (ตรวจสอบรายการ transaction ว่ามีรายการหลัง T4 หรือไม่)
- [ ] ผู้มีอำนาจที่รับผิดชอบ (§1 บทบาท A) อนุมัติการ rollback อย่างชัดเจน
- [ ] คืนสถานะการเขียนข้อมูลของ AppSheet **โดยใช้กลไกปฏิบัติการที่อนุมัติแล้ว
      เดียวกัน**กับที่ใช้ล็อกระบบตอน T0 แต่ทำในทิศทางย้อนกลับ
- [ ] สื่อสารการเปลี่ยนกลับของแหล่งข้อมูลจริง (source of truth) ให้เจ้าหน้าที่
      ทุกคนทราบอย่างชัดเจน — ห้ามปล่อยให้เจ้าหน้าที่ต้องเดาเอง
- [ ] เก็บรักษาหลักฐาน readiness/decision/audit ทั้งหมดไว้ตามเดิม — ห้ามลบ
      หรือแก้ไขเพื่อ "รีเซ็ต" สำหรับความพยายามครั้งต่อไป
- [ ] บันทึกสาเหตุของการ rollback
- [ ] แก้ไขปัญหาต้นเหตุ
- [ ] สร้าง/รัน readiness process ใหม่ (`CutoverReadinessRun` ใหม่) ก่อนที่จะ
      พยายามเปลี่ยนระบบอีกครั้ง

**ห้ามลบหลักฐานเพื่อ "รีเซ็ต" ความพยายามเปลี่ยนระบบที่ล้มเหลว**

---

## 10. Rollback — หลังมีรายการ production รายการแรก (Forward-fix)

**ขอบเขต (OD-PR23-4): หลังจากมีรายการปฏิบัติการจริงรายการแรกถูกยอมรับแล้ว
การ rollback แบบเต็มรูปแบบไม่ใช่แนวทางเริ่มต้น — การแก้ไขไปข้างหน้าแบบควบคุม
(controlled forward-fix) คือแนวทางเริ่มต้นแทน**

- [ ] **ห้าม**กลับไปเขียนข้อมูลใน AppSheet แบบไม่ควบคุม
- [ ] คงแอปพลิเคชันใหม่ไว้เป็นแหล่งข้อมูลจริงเชิงปฏิบัติการ เว้นแต่ผู้มีอำนาจ
      จัดการเหตุการณ์ (incident authority) จะตัดสินใจเป็นอย่างอื่นอย่างชัดเจน
      (เป็นการตัดสินใจที่แยกต่างหาก และต้องการอำนาจมากกว่าการตัดสินใจ NO-GO
      ปกติ)
- [ ] ระบุรายการ/เครื่องมือที่ได้รับผลกระทบให้ชัดเจน
- [ ] ใช้กลไกแก้ไข/audit ที่มีอยู่แล้วในแอปพลิเคชันตามความเหมาะสม — ห้ามแก้ไข
      ข้อมูลแบบเฉพาะกิจ
- [ ] บันทึกหลักฐานของเหตุการณ์/การกู้คืน
- [ ] หลีกเลี่ยงการสร้างรายการ Issue/Receive ซ้ำระหว่างการตรวจสอบ
- [ ] ห้ามคัดลอกรายการระหว่าง AppSheet กับแอปพลิเคชันแบบเฉพาะกิจโดยเด็ดขาด

**หากยังไม่มีกระบวนการจัดการเหตุการณ์/กู้คืนที่อนุมัติแล้วสำหรับความล้มเหลวที่พบ
เจอ ต้อง escalate (ยกระดับ) ทันที** — คู่มือนี้ไม่สามารถแทนที่กระบวนการตอบสนอง
เหตุการณ์จริงที่ยังไม่ได้กำหนดไว้ได้

## 11. เครื่องหมายรายการ production รายการแรก (First production transaction marker)

เนื่องจากความหมายของ rollback (§9 เทียบกับ §10) ขึ้นอยู่กับขอบเขตนี้โดยตรง ผู้
ปฏิบัติงานต้องระบุและบันทึกข้อมูลต่อไปนี้ สำหรับ**รายการปฏิบัติการจริงรายการแรก
ที่ได้รับการยอมรับหลัง T4**:

```
เวลา (Timestamp):                                          __________________
รหัสรายการ (BorrowTransaction identifier):                  __________________
ผู้ปฏิบัติงาน (Actor):                                       __________________
BCM Code ของเครื่องมือ (หรือ identifier ทางธุรกิจอื่นที่ปลอดภัย —
ห้ามใช้ข้อมูลระบุตัวผู้ป่วยโดยเด็ดขาด):                       __________________
```

**ห้ามบันทึกข้อมูล PHI (ข้อมูลที่ระบุตัวผู้ป่วยได้) ในเครื่องหมายนี้หรือในแบบฟอร์ม
ใดๆ ของคู่มือนี้เด็ดขาด** เครื่องหมายนี้เป็นหลักฐานเชิงปฏิบัติการสำหรับคู่มือนี้
เท่านั้น — ไม่จำเป็นต้อง และต้องไม่กลายเป็น feature ใหม่ของระบบ/ฐานข้อมูล ไม่มี
การเปลี่ยนแปลง schema ใดๆ ที่ PR23F เพิ่มเข้ามาเพื่อรองรับสิ่งนี้

## 12. ขั้นตอน Pilot (OD-PR23-5)

Pilot เริ่มต้นด้วย**หอผู้ป่วยนำร่องเพียงหอเดียวที่ควบคุมได้ (one controlled
Pilot Ward)** ซึ่งเลือกจาก Ward/department master data ที่มีอยู่แล้ว คอลัมน์
`แผนกที่ยืม` จากระบบเดิมอาจช่วยระบุว่าควรใช้ Ward ใดที่มีอยู่แล้ว แต่**ข้อความดิบ
จากระบบเดิมจะไม่มีการสร้าง Ward ใหม่โดยอัตโนมัติเด็ดขาด**

**ระยะเวลา Pilot ไม่ได้ถูกกำหนดตายตัวเป็นจำนวนวัน** ห้ามวางแผนหรือสื่อสาร
ระยะเวลาคงที่ เช่น "5 วัน" หรือ "1 สัปดาห์" Pilot จะสิ้นสุดเมื่อหลักฐานการยอมรับ
ด้านล่างครบถ้วน ไม่ว่าจะใช้เวลานานเท่าใด — Pilot**ไม่จำเป็น**ต้องรอให้เครื่องมือที่
ยืมออกไปทั้งหมดถูกส่งคืนก่อน

### เกณฑ์การสิ้นสุด Pilot (หลักฐานขั้นต่ำที่ต้องมีครบทุกข้อ)

- [ ] เข้าสู่ระบบ/ปฏิบัติงานที่ได้รับอนุญาตสำเร็จ
- [ ] ค้นหาด้วย BCM ใช้งานได้
- [ ] ค้นหาด้วย QR ใช้งานได้ โดยใช้ Item Number เดิมที่มีอยู่แล้ว (ไม่มีการพิมพ์
      QR ใหม่)
- [ ] Issue เครื่องมือจาก Equipment Pool ไปยังหอผู้ป่วยนำร่องสำเร็จ
- [ ] บันทึก Ward ผู้รับรายการแรก (first-receiving-Ward) ถูกต้อง (§13)
- [ ] ประวัติรายการ (Transaction History) แสดงถูกต้อง
- [ ] มีวงจร Issue → Receive ที่สมบูรณ์อย่างน้อยหนึ่งครั้งที่เป็นตัวแทน
- [ ] Receive เครื่องมือที่ใช้งานได้แล้วให้ผล `AVAILABLE_AT_POOL` ถูกต้อง
- [ ] ตรวจสอบพฤติกรรม Receive เครื่องมือชำรุด**เฉพาะเมื่อเกิดกรณีชำรุดจริงตาม
      ธรรมชาติระหว่าง Pilot เท่านั้น** — ดู §14 ห้ามสร้างกรณีชำรุดขึ้นมาเอง หากไม่
      เกิดกรณีชำรุดจริง อาจใช้กระบวนการ non-production/UAT ที่อนุมัติแล้วในการ
      ตรวจสอบ workflow นี้แทน โดยไม่แตะต้องเครื่องมือ production จริง
- [ ] ไม่มีข้อบกพร่องระดับ Critical/Blocking ที่ยังไม่แก้ไข
- [ ] เจ้าของงานเชิงปฏิบัติการ (operational Owner) ที่รับผิดชอบยืนยันว่า
      workflow พร้อมใช้แทน AppSheet สำหรับขอบเขต Pilot นี้แล้ว

### ข้อชี้แจงเรื่องการโอนย้ายระหว่าง Ward (ไม่ใช่ feature ใหม่)

ระบบบันทึกเฉพาะ Ward ผู้รับรายการ**แรก**เท่านั้นสำหรับแต่ละรายการ หากเครื่องมือ
เคลื่อนย้ายในภายหลัง Equipment Pool → Ward A → Ward B → Equipment Pool
รายการจะยังคงบันทึก **Ward A** เป็น Ward ผู้รับ Ward A → Ward B **ไม่ใช่**
workflow การโอนย้ายที่ถูกติดตาม — ไม่มี endpoint, ตาราง, สถานะ lifecycle หรือ
UI สำหรับการโอนย้ายใน V1 การ Receive ครั้งสุดท้ายกลับสู่ Equipment Pool คือจุด
ปิดรายการ ห้ามอธิบายเรื่องนี้แตกต่างไปจากนี้กับเจ้าหน้าที่ระหว่าง Pilot หรือ
Production

### ผลลัพธ์ Pilot (แบบฟอร์มปฏิบัติการ — ยังไม่กรอกในเอกสารนี้)

```
หอผู้ป่วยนำร่อง (Pilot Ward):                    __________________
วันเริ่ม Pilot:                                    __________________
หลักฐานอ้างอิงของ Pilot:                          __________________
ข้อบกพร่องระดับ Blocking:                         __________________
ข้อค้นพบที่ยังไม่แก้ไข (non-blocking):             __________________
เจ้าของงานเชิงปฏิบัติการ (Operational Owner):     __________________
ผลการตัดสินใจ Pilot:  [ ] PASS   [ ] NO-GO / ขยายเวลา Pilot
```

รีโพซิทอรีนี้จะไม่ และต้องไม่ ทำเครื่องหมายแบบฟอร์มนี้เป็น PASS ในเอกสารนี้เอง —
กรอกได้เฉพาะตอนปฏิบัติงาน Pilot จริงเท่านั้น

## 13. สิ่งที่ไม่เปลี่ยนแปลง — QR / Identity

คงไว้ทุกประการ ไม่มีการเปลี่ยนแปลงจากคู่มือนี้หรือจาก PR23 slice ใดก่อนหน้านี้:

- **UUID** — identity หลักภายในระบบ
- **BCM Code** — identifier ที่ใช้งานเชิงธุรกิจ
- **Item Number** — ค่าที่ใช้ค้นหาด้วย QR code ของโรงพยาบาลที่มีอยู่แล้ว
- **Asset Number** — identifier แยกต่างหาก

**QR code ของโรงพยาบาลที่มีอยู่แล้วไม่มีการเปลี่ยนแปลง** ห้ามสั่งให้เจ้าหน้าที่พิมพ์
QR code ใหม่สำหรับการเปลี่ยนระบบ

---

## 14. สิ่งที่ไม่เปลี่ยนแปลง — วงจรสถานะเครื่องมือ (Equipment lifecycle)

วงจรสถานะยังคง**เหมือนเดิมทุกประการ**:

```
AVAILABLE_AT_POOL      (พร้อมใช้งานที่ส่วนกลาง)
ISSUED_TO_WARD          (ถูกยืมออกไปยังหอผู้ป่วย)
UNAVAILABLE_DEFECTIVE   (ชำรุด ใช้งานไม่ได้)
DECOMMISSIONED          (ปลดระวาง)
```

"การทำความสะอาด" ไม่ใช่สถานะ lifecycle (การทำความสะอาดเครื่องมือเป็นส่วนหนึ่ง
ของ workflow Receive ไม่ใช่สถานะที่ติดตามแยกต่างหาก) การ Receive เครื่องมือที่
ใช้งานได้จะให้ผล `AVAILABLE_AT_POOL`; การ Receive เครื่องมือชำรุดจะให้ผล
`UNAVAILABLE_DEFECTIVE` การ Issue คือ Equipment → Ward → ยืนยัน →
`ISSUED_TO_WARD` **ห้ามมีสถานะเพิ่มเติมใดๆ ปรากฏในคู่มือนี้หรือในการสื่อสารเรื่อง
การเปลี่ยนระบบ**

---

## 15. การตรวจสอบหลังเปลี่ยนระบบ (Post-cutover validation)

ปฏิบัติทันทีหลัง T4 โดยใช้ความสามารถที่มีอยู่แล้วในแอปพลิเคชันเท่านั้น — ไม่มีกลไก
ใหม่:

- [ ] เข้าสู่ระบบสำเร็จสำหรับทั้ง 3 role
- [ ] ค้นหาเครื่องมือด้วย BCM Code
- [ ] ค้นหาด้วย QR โดยใช้ Item Number เดิม
- [ ] Issue เครื่องมือไปยัง Ward
- [ ] Receive เครื่องมือที่ใช้งานได้ → `AVAILABLE_AT_POOL`
- [ ] Receive เครื่องมือชำรุด → `UNAVAILABLE_DEFECTIVE`
- [ ] ประวัติรายการแสดงถูกต้อง รวมถึงประวัติข้อมูลเดิมในมุมมองรวมเดียวกัน
- [ ] Reconciliation run/finding/sign-off แสดงถูกต้อง (หน้าจอ PR22F)
- [ ] พฤติกรรมสิทธิ์การเข้าถึง (role permission) ถูกต้องสำหรับแต่ละ role
- [ ] มีการสร้าง audit record สำหรับทุกการกระทำข้างต้น

**ใช้เครื่องมือทดสอบ/สาธิต หรือรายการจริงจำนวนน้อยที่ตกลงกันไว้ล่วงหน้าและติด
ป้ายชัดเจนเท่านั้นสำหรับการตรวจสอบนี้** — ใช้แนวทางเดียวกับ demo-seed ที่มีอยู่
แล้วในรีโพซิทอรี (`app.scripts.seed`) **ห้ามสร้างกรณีเครื่องมือชำรุดปลอมขึ้นมาเพื่อ
ทดสอบ workflow Receive เครื่องมือชำรุดโดยเด็ดขาด** ให้ใช้กระบวนการ
non-production/test ที่อนุมัติแล้ว หรือใช้กรณีชำรุดจริงเมื่อเกิดขึ้นตามธรรมชาติ
ห้ามแก้ไขเครื่องมือ production จริงเพียงเพื่อทดสอบระบบ

## 16. ข้อแตกต่างระหว่าง "PR23 เสร็จสมบูรณ์" กับ "พร้อมใช้งาน Production"

> **"Roadmap PR23 (ความสามารถของแอปพลิเคชัน) เสร็จสมบูรณ์แล้ว" ไม่ใช่
> ข้อความเดียวกันกับ "พร้อมใช้งาน Production (Production Ready)"**

การใช้งาน production จริงยังต้องการหลักฐานจริงตาม
`docs/audits/04-consolidated-implementation-plan.md` Part I (Production
Readiness) รวมถึง (ตามความเกี่ยวข้อง):

- ได้รับ sign-off จาก UAT แล้ว
- ได้รับ sign-off จาก Pilot แล้ว (§12)
- backup/restore ผ่านการทดสอบจริงแล้ว (ไม่ใช่แค่เขียนเป็นเอกสาร — §17)
- ยืนยันการตั้งค่า production ที่ปลอดภัยแล้ว
- เลือกเป้าหมาย production deployment จริงแล้ว (§18)
- ตรวจสอบรายชื่อผู้ใช้งาน/สิทธิ์จริงกับรายชื่อ production จริงแล้ว
- มีหลักฐานเรื่อง concurrency ที่ใกล้เคียงสภาพ production จริง
- มีระบบ monitoring/structured logging พร้อมใช้งาน
- มีเอกสารกระบวนการสนับสนุน/กู้คืนระบบ
- การกระทบยอด inventory/สถานะปัจจุบันเสร็จสมบูรณ์

**ห้ามอ้างว่ารายการใดข้างต้นผ่านแล้ว เว้นแต่มีหลักฐานจริงจากรีโพซิทอรี/การ
ปฏิบัติงานยืนยัน** คู่มือนี้ให้เพียงช่องสำหรับกรอกหลักฐาน — ไม่สามารถกรอกให้เอง
ได้

## 19. แผนการสื่อสาร (Communication plan)

| จุดตรวจสอบ | ข้อความที่ต้องสื่อสาร |
|---|---|
| ก่อน T0 | ประกาศเวลาที่จะเริ่มช่วงหยุดระบบให้เจ้าหน้าที่ที่เกี่ยวข้องทุกคนทราบ |
| ที่ T0 | ยืนยันว่าการเขียนข้อมูลปฏิบัติการใน AppSheet หยุดแล้ว |
| ที่ T3 | สื่อสารผลการตัดสินใจที่บันทึกไว้: GO หรือ NO_GO |
| ที่ T4 | ประกาศว่าแอปพลิเคชันใหม่เป็นระบบเดียวที่ใช้บันทึกข้อมูลปฏิบัติการแล้ว |

**หลีกเลี่ยงข้อความที่คลุมเครือ เช่น "ใช้ระบบใดก็ได้"** ในทุกจุดตรวจสอบข้างต้น

ระบุให้ชัดเจน

## 21. ความปลอดภัย / การจัดการข้อมูล (Security / data handling)

คู่มือนี้ห้ามบันทึกสิ่งต่อไปนี้ในช่อง/แบบฟอร์ม/บันทึกหลักฐานใดๆ ที่กล่าวถึงข้างต้น
โดยเด็ดขาด:

- รหัสผ่าน (Passwords)
- Access token
- ข้อมูลรับรองฐานข้อมูล (database credentials)
- ข้อมูลระบุตัวผู้ป่วย หรือข้อมูลที่ระบุตัวผู้ป่วยได้ใดๆ
- ข้อมูล PHI ดิบทุกประเภท
- เนื้อหาไฟล์ workbook ดิบที่ไม่มีการควบคุม

**ให้ใช้ reference/ID/checksum แทน** — โมเดลหลักฐานของแอปพลิเคชันเอง (run
ID, sign-off ID, source checksum) มีวินัยนี้อยู่แล้ว คู่มือนี้ปฏิบัติตามแนวทางเดียวกัน
ไม่สร้างแนวทางคู่ขนานขึ้นมาใหม่

## 22. ตารางอ้างอิงสถานการณ์ที่คลุมเครือ (Ambiguous-scenario quick reference)

| สถานการณ์ | สิ่งที่ต้องทำ |
|---|---|
| ทุก gate ผ่าน, warning ถูก acknowledge ครบแล้ว | ดำเนินการ `GO` → T4 (§5/§7) |
| Gate D (หรือ mandatory gate ใดๆ) มี BLOCKER | `GO` เป็นไปไม่ได้ในเชิงโครงสร้าง — backend จะปฏิเสธเอง ให้แก้ไขช่องว่างต้นเหตุ ห้ามพยายามข้าม |
| ไม่สามารถทำให้ AppSheet เป็น read-only ได้จริงที่ T0 | STOP / NO-GO — ห้ามดำเนินการต่อจาก T0 (§5) |
| พบความไม่ตรงกันของสถานะปัจจุบันที่ T2 | STOP แก้ไขผ่านระบบ/กระบวนการเจ้าของข้อมูล ประเมินใหม่ (§5/§8) |
| ขอ rollback ก่อนมีรายการ production รายการแรก | ทำตาม §9 |
| พบความล้มเหลวหลังมีรายการ production รายการแรก | ทำตาม §10 (forward-fix) ห้าม reverse migration อัตโนมัติ |
| Pilot มีการ Issue สำเร็จแต่เครื่องมือยังไม่คืนครบ | Pilot ยังสามารถสิ้นสุดได้หากเกณฑ์อื่นทุกข้อ (§12) ครบถ้วนแล้ว |
| ไม่เกิดกรณีเครื่องมือชำรุดตามธรรมชาติระหว่าง Pilot | ห้ามสร้างกรณีขึ้นมาเอง — ใช้กระบวนการ non-production/UAT ที่อนุมัติแล้วแทน หรือปล่อยเกณฑ์นั้นค้างไว้จนกว่าจะเกิดขึ้นจริง |
| ยังไม่มีหลักฐานการทดสอบ backup/restore | ไม่สามารถอ้างว่า production พร้อมใช้งานได้ — Gate A / Production Readiness ยังคงถูกบล็อก (§17) |
| ยังไม่ได้เลือกผู้ให้บริการ production deployment | Roadmap PR23 (ความสามารถของแอปพลิเคชัน) ยังถือว่าเสร็จสมบูรณ์ได้ แต่ความพร้อมของ Production execution ยังไม่ได้ (§16/§18) |
